# Architecture

Status: DNS seedlist v0.2 release-ready. This document must be updated in the same activity that changes an architectural contract.

## Design constraints

The production implementation targets Lua 5.4 with 64-bit integers. Driver, BSON, wire protocol, SDAM, CMAP, selection, retry, and transaction behavior are pure Lua. A coroutine-aware runtime interface isolates clocks, cancellation, tasks, locks, environment access, sockets, TLS, entropy, hashing, HMAC, and PBKDF2. The supported default adapter is Copas 4.11 with LuaSocket, LuaSec, and an OpenSSL-backed crypto module.

The top-level module enforces the Lua version and integer-width constraints at load time. The public module version, handshake driver version, release rockspec, README, and changelog share the DNS seedlist release version `0.2.0`; the LuaRocks revision is `0.2.0-1`. The LuaRocks package maps every production module below `src/mongodb`; its package gate builds a source rock from the current checkout, installs it in a temporary tree, removes workspace paths from Lua's module search, and exercises the documented client, BSON, runtime, bulk-model, and index-model entry points. Busted specifications live under `spec`, and Luacheck enforces Lua 5.4 plus project style. Verification has two explicit compositions: `make check-fast` runs unit, integration, static unified, stress, compatibility-matrix, package-install, lint, rockspec, and planning gates, while `make check-full` adds live unified execution and coverage. `make check` remains the full release alias. Unified fixture parsing and schema validation occur once in either composition rather than being repeated by the inventory gate. Per-commit Actions run the fast composition on Ubuntu and macOS and probe the oldest standalone plus newest replica-set compatibility boundaries. Complete Linux conformance and all six compatibility rows run nightly; complete macOS conformance runs weekly, and both platforms can be requested manually for an exact commit. Superseded per-commit and full-conformance runs are canceled by workflow/ref concurrency groups.

The public entry point is `require("mongodb")`. Modules and functions use `snake_case`; stateful public values use colon methods. Operational APIs return `value` on success or `nil, err` on failure. Structured errors have stable categories, codes, labels, causal chains, and server details. Programmer misuse and broken internal invariants may raise.

### Structured error contract

`mongodb.error` constructs readonly error values rather than an exception hierarchy. Every value has a known `category` and non-empty `message`; it may also carry a numeric MongoDB `code`, `code_name`, ordered unique `labels`, a structured `cause`, server/topology context, timeout/retryability flags, and recursively readonly `details`. Diagnostic string conversion intentionally excludes details so arbitrary server documents and secrets are not rendered accidentally.

Category, label, timeout, and retryability predicates let execution layers classify failures without parsing messages. Adding or removing a label creates a new value and preserves the original causal value. Invalid constructor fields, unknown categories/options, and attempts to mutate public values are programmer errors and raise immediately. Network, protocol, server, selection, authentication, pool, BSON, and other operational failures must construct one of these values and return it as `nil, err`.

### Runtime interface

Core modules receive one validated runtime value and never import a scheduler, socket, TLS, entropy, or crypto library directly. The interface groups capabilities by responsibility:

| Capability | Required operations |
| --- | --- |
| Clock | monotonic `now`, Unix `wall_time`, and coroutine-aware `sleep` |
| Cancellation | create tokens with idempotent cancellation and ordered listeners |
| Tasks | spawn, await, and cancel coroutine work |
| Locks | create locks with explicit acquire/release transitions |
| DNS | resolve SRV and TXT records with TTL and character-string boundaries intact |
| Sockets | connect and return sockets supporting partial read/write and idempotent close |
| TLS | wrap an established socket without leaking adapter details upward |
| Entropy | return an exact number of random bytes |
| Crypto | MD5, SHA-1/SHA-256, corresponding HMAC, and PBKDF2 variants |

Deadlines are absolute values from the runtime's monotonic clock. Unix wall time is a separate capability for BSON ObjectId generation and other protocol timestamps; it is never used for elapsed-time decisions. Shared helpers derive deadlines, clamp remaining time to zero, and classify cancellation before expiration as structured operational errors. Adapter validation treats a missing function as programmer misconfiguration.

`mongodb.runtime.fake` implements the entire boundary without external dependencies. Its clock advances only under test control, tasks execute in queue order, DNS results and socket reads/partial writes consume scripts, cancellation is synchronous, and TLS/entropy/crypto calls are recorded or scripted. DNS scripts retain SRV targets, ports, priorities, weights, and TTLs or ordered TXT character strings and TTLs; an empty record array is a successful no-answer result. Missing fake scripts raise because they indicate a malformed test, while scripted operational failures return `nil, err`.

`mongodb.runtime.copas` implements the scheduling boundary with Copas 4.11 futures, pauses, non-reentrant locks, and LuaSocket providers. It clamps Copas time so the driver never observes backward movement, wakes sleeping tasks on cancellation, and polls contended locks, socket waits, and DNS receives so cancellation remains bounded. `mongodb.runtime.copas_dns` discovers recursive nameservers from `resolv.conf` or accepts an injected adapter-local list, sends coroutine-safe UDP SRV/TXT queries, retries truncated answers over TCP, and normalizes wire replies without exposing provider sockets to configuration, discovery, or topology code. Query IDs come from runtime entropy; one finite query budget is shared across configured nameservers and any TCP fallback. NXDOMAIN and a successful empty answer return an empty record array, response codes return network errors, malformed replies return protocol errors, and caller deadlines or cancellation retain their existing structured categories. Its default `mongodb.runtime.openssl` provider supplies cryptographically secure entropy plus MD5, SHA, HMAC, and PBKDF2 through luaossl; MD5 exists only for MongoDB's legacy SCRAM-SHA-1 password transform. Its default TLS provider is the LuaSec adapter described below. Callers may inject conforming providers without changing core code.

`mongodb.run` is the standalone-program convenience boundary over that adapter. It validates that the caller supplies a function, rejects ownership when a Copas loop is already active, runs the callback in a Copas coroutine, preserves every callback return value including nil positions, and rethrows callback errors without scheduler-specific wrapping. It does not create or implicitly close clients; applications retain explicit resource lifecycles, while frameworks that already own Copas continue to call the normal client API inside their existing loop.

### Exact TCP transport

`mongodb.network.transport` owns runtime-neutral connection lifecycle and exact byte transfer. It repeatedly calls the runtime socket's partial read/write operations until the requested byte count is satisfied, checking the same absolute monotonic deadline and cancellation token before every attempt. EOF, network failure, timeout, and cancellation remain distinct structured errors. Length-prefixed frame reads validate the four-byte size before allocating or reading the remainder, and close is idempotent on every path.

`mongodb.runtime.copas_socket` is the runtime-specific LuaSocket adapter. It wraps non-blocking TCP sockets with Copas, applies the remaining absolute deadline to connect/read/write waits, and bounds waits with a short poll interval when cancellation is enabled. LuaSocket error strings are translated at this boundary and never leak scheduler or socket objects into wire, topology, or command code. A loopback integration test exercises the real Copas scheduler and LuaSocket provider with deliberately split response writes.

### LuaSec TLS transport

`mongodb.runtime.luasec` converts normalized per-connection TLS policy into a LuaSec client context, while `mongodb.runtime.copas_socket` owns the runtime-specific SNI and asynchronous handshake. The core transport supplies the same absolute deadline and cancellation token used for TCP establishment; handshake polling bounds cancellation latency without resetting that deadline. A successful upgrade preserves the abstract partial read/write socket contract, so no core module imports LuaSec or sees its socket objects.

Certificate-chain and hostname verification are enabled by default. A custom CA bundle takes precedence; otherwise the adapter uses `SSL_CERT_FILE`, then common Unix CA bundle paths, with `SSL_CERT_DIR` as a directory fallback. If no trust store is available, context construction returns a structured configuration error rather than silently disabling verification. DNS connections send SNI. Hostname matching gives subject alternative names precedence over the common name, supports exact DNS names, a wildcard covering exactly one leftmost label, and canonical IPv4/IPv6 subject alternatives.

A combined client certificate/private-key PEM may be supplied with an optional decryption password. Context and handshake failures are converted to credential- and path-free structured errors. `allow_invalid_hostnames` disables only name matching; `allow_invalid_certificates` disables chain verification and therefore name matching; `insecure` disables both. LuaSec 1.3 does not expose OCSP endpoint or CRL revocation checking through this adapter, so `disable_ocsp_endpoint_check` and `disable_certificate_revocation_check` currently document intent but do not alter behavior. TLS compression and renegotiation are disabled where the linked OpenSSL supports those controls.

### BSON values and codec

`mongodb.bson` represents documents and arrays with explicit immutable containers. Documents retain insertion order and duplicate keys; indexed access returns the last matching key while `keys`, `entries`, and `iter` preserve every wire entry. Arrays are distinct from documents, and `bson.null` is distinct from absent Lua values. Constructors copy their input so later mutation cannot change an in-flight command.

The codec accepts only an ordered document at its root and encodes Lua strings as BSON strings, integral numbers as the smallest signed BSON integer, non-integral numbers as doubles, and explicit wrappers for arrays, binary data, and null. Immutable tagged values represent ObjectId, signed-millisecond UTC datetime, regular expression, timestamp, JavaScript code with optional ordered scope, Symbol, DBPointer, Undefined, MinKey, and MaxKey. Binary values retain every subtype and apply the legacy subtype-2 nested length rule. Decoding produces the same unambiguous value model. Arbitrary Lua tables are rejected because neither their intended BSON type nor their iteration order is defined.

Decoded int32, int64, and double values use explicit immutable wrappers carrying both the Lua value and original little-endian bytes. Their constructors also let callers force a numeric wire type; unwrapped Lua integers still select the smallest signed representation. This preserves small int64 values, double negative zero, and NaN payload bits across a decode/encode cycle without overloading arithmetic operators.

Decimal128 is stored as its exact 16-byte Binary Integer Decimal representation. String conversion uses decimal-digit and byte-array arithmetic in Lua, applies the 34-digit half-even context's exactness, exponent, and clamping rules, and never passes through a binary float. NaN variants and non-canonical encodings retain their input BID even when their required diagnostic string is lossy. The pinned official Decimal128 corpus is the conformance source.

ObjectId generators are stateful values constructed from an injected runtime. They obtain a five-byte generator identifier and three-byte initial counter from `runtime.entropy`, read seconds from `runtime.clock.wall_time`, and increment the 24-bit counter without importing platform time or randomness into BSON code. ObjectId, datetime, timestamp, regex, and binary values implement equality or ordering where their BSON semantics define it.

All lengths and element payloads are checked against their containing frame before reading. Invalid document, string, binary, code-scope, boolean, terminator, trailing-byte, UTF-8, and unsupported-type encodings return structured `bson` errors carrying a one-based byte offset. Codec options bound document, string, binary, and nesting sizes; the defaults are 16 MiB for each size and 100 document levels. UTF-8 validation is on by default and may be disabled explicitly for byte-preserving diagnostic work. Degenerate array keys and unordered regex flags accepted by the BSON corpus are normalized when re-encoded.

### Ordered JSON and Extended JSON

`mongodb.bson.json` parses JSON directly into the ordered BSON value model, including explicit arrays, null, and exact numeric wrappers. The recursive-descent parser validates JSON number grammar, UTF-8, escapes and surrogate pairs, trailing input, and configurable input/string/depth limits. It does not pass object pairs through an unordered Lua table.

Extended JSON conversion recognizes canonical, relaxed, and permitted degenerate representations for every BSON wire value. Known wrapper keys require their exact fields and types; unknown dollar-prefixed documents remain ordinary documents. Generation supports canonical and relaxed modes, preserves field order, uses canonical Base64/subtype encoding, and emits ISO-8601 UTC datetimes only where relaxed Extended JSON permits them.

BSON binary subtype 9 has a small public vector view rather than a numerical-library dependency. `mongodb.bson.vector` validates dense Lua input and emits the mandatory dtype and padding bytes followed by little-endian INT8, FLOAT32, or PACKED_BIT data. `binary:as_vector` validates the same invariants when explicitly unpacking generic binary data and returns an immutable record whose numeric data is an explicit BSON array. FLOAT32 payload lengths must be divisible by four; non-bit padding, out-of-range values, empty padded bit vectors, and non-zero ignored bits are rejected. All 22 pinned vectors execute from numeric input through canonical BSON bytes and back.

### Unified schema validation

`mongodb.unified.schema` compiles an ordered JSON Schema document into an immutable validator. The implemented draft 2019-09 subset covers the constructs exercised by unified schema 1.28: local references, object properties and required fields, additional and pattern properties, array/property bounds, primitive types, enums, constants, the version and KMS-provider patterns, and `allOf`, `oneOf`, and `not`. Schema violations return structured `configuration` errors with both a JSONPath-like document path and a JSON Pointer schema path.

The schema gate loads only fixture envelopes in Python and performs parsing and validation in Lua. Both `valid-pass` and `valid-fail` are schema-valid—the latter are reserved for later runner failures—while every file in `invalid` must be rejected. The meta-runner gate covers all 320 distinct JSON fixtures pinned with the specification checkout; equivalent YAML copies are not counted twice. A separate integration-fixture gate passes all 535 pinned JSON files through the same ordered Extended JSON parser, rejects schema versions outside the supported 1.28 line, validates each document against schema 1.28, and inventories all 2,531 contained tests.

`mongodb.unified.runner` is the execution-neutral core. Each test creates a runner with an isolated entity registry, environment facts, entity factories, per-entity-kind operation handlers, and an optional outcome reader. Entity IDs are unique and typed; missing entities, unsupported entity kinds, unsupported operations, and unknown match operators return visible `configuration` errors with document paths. This registry/dispatch boundary lets later slices connect real driver objects without teaching the runner about transports.

`mongodb.unified.lifecycle` is the test-file orchestrator around that core. It evaluates file and test `runOnRequirements` plus `skipReason` before setup, delegates `initialData` and outcome reads to one injected internal-client adapter, and creates a fresh runner and entity map for every executed test. Operations finish before registered listener/failpoint finalizers; only a successful operation phase proceeds to event and outcome assertions. An entity observer then receives the still-live isolated map before teardown. Every path—including an operation or assertion failure—runs remaining finalizers and destroys entities in reverse registration order, ending sessions, closing clients and cursors, and awaiting threads by default or through kind-specific cleanup adapters. Failures are reported per test and never stop subsequent tests. The lifecycle owns no socket, deployment, or scheduler implementation; environment facts, runtime, internal commands, entities, and operations remain injected boundaries.

Run-on requirements compare numeric version components and environment topology, authentication, serverless, server-parameter, and encryption facts. Matching implements strict nested documents, root subset matching, flexible BSON numbers, exact arrays, and every unified operator: `$$exists`, `$$type`, `$$matchesEntity`, `$$matchesHexBytes`, `$$unsetOrMatches`, `$$sessionLsid`, `$$lte`, `$$matchAsDocument`, and `$$matchAsRoot`. Hexadecimal-byte expectations compare decoded bytes with string results, session IDs are resolved through the typed entity boundary, and entity matches recursively apply normal matcher semantics. Iterable result documents retain root subset matching, while outcome documents require exact fields but ignore BSON key order. The meta gate executes all 19 dedicated upstream matcher pass/fail cases plus pinned GridFS and session operator expectations without a server.

Thread entities schedule work through the injected runtime task interface, and bounded loops record iteration and success counters as BSON entities. Unit tests use the deterministic fake runtime and fake entity/operation handlers; no runner-core test opens a network connection.

Entity operation adapters are descriptors with a handler, an explicit accepted-argument set, optional result coercion, and an optional saved-entity kind. The runner resolves `session` arguments through the typed entity registry before dispatch, rejects unknown arguments before a handler can perform I/O, ignores only structured operational failures when requested, and refuses missing or unsupported saved results. BSON results are inferred; find cursors, command cursors, and change streams require an explicit result kind.

Expected-error processing asserts client origin, timeout status, case-insensitive message and code-name matching, numeric codes, included and omitted labels, exact write-error indices, ordered write-concern errors, root-level server responses, and partial results. Unknown expectation fields and unstructured handler failures are configuration errors. The meta gate executes 17 applicable upstream operation pass/fail cases for error responses, ignored and unexpected failures, empty and unsupported operations, dynamic entities, and invalid entity references; focused fakes exercise every remaining expected-error field and typed-result boundary.

The filesystem-facing unified CLI is a Python envelope around the Lua schema/runner layers, like the BSON corpus loader. It discovers every pinned path matching `*/tests/unified/*.json`, the direct Stable API test directory, and the read/write-concern operation directory; validates exact coverage against `spec/unified/capabilities.json`; applies repeatable glob include filters; and emits versioned reports. Schema validation, per-test inventory, meta-runner execution, and driver execution have distinct report types. Inventory rows use `fixture/path.json::test[N]` identities; execution counters separately name passes, failures, environment skips, unsupported deferrals, scope exclusions, and invalid or incompatible inputs. Zero executed tests always sets `conformant` to false, even when every classification is valid. Runnable identities are grouped by fixture and deployment environment before crossing the Lua process boundary. One bridge invocation loads the fixture and creates one internal-client lifecycle, while `mongodb.unified.lifecycle` still resets initial data and creates and destroys a fresh runner, entity map, clients, sessions, cursors, listeners, threads, and failpoints for every selected test. The bridge returns one machine-readable row for every exact identity; unknown, duplicate, or omitted rows fail the complete batch instead of disappearing into an aggregate count.

Complete execution may be partitioned with an explicit shard count and zero-based index. The first 64 bits of the fixture path's SHA-256 digest select the shard, so all tests inherited from one fixture remain together and the assignment is stable across Python versions and operating systems. Shard reports carry their count and index but deliberately omit global ratchets. Aggregation requires every index exactly once, rejects unknown, duplicate, missing, malformed, wrongly assigned, or classification-changing rows, rebuilds the canonical report in manifest order, and only then enforces the same classified, runnable, and passing ratchets as an unsharded execution.

Execution reports keep performance observations in a top-level `timings` object, separate from test identities, statuses, summaries, and ratchets. A monotonic clock measures preprocessing setup, environment provisioning, each fixture-and-environment batch, and total elapsed execution including cleanup; the report also derives the ten slowest fixture groups. Fixture-group rows are canonicalized by fixture and environment, while the slowest view orders by duration with stable identity tie-breakers. Shard aggregation sums setup, environment, and total worker time, concatenates the disjoint fixture observations, and derives a fresh slowest view instead of trusting shard summaries. These measurements diagnose runner cost but never determine conformance.

The manifest records the pinned specifications commit and assigns each individual `fixture/path.json::test[N]` identity a status, pending owning activity, and concrete reason when it is not runnable. A SHA-256 fingerprint binds the fixture-level setup and test body to the classification. Extracted entities, operations, special runner operations, arguments, event types, matcher operators, outcome use, log expectations, and topology requirements make new upstream capabilities explicit. Missing or stale entries, unknown capabilities or statuses, completed deferral owners, empty reasons, empty discovery, and runnable tests without an executor are hard failures. Classified, runnable, and passing count ratchets cannot move backward.

All 2,531 tests in the 535 discovered integration fixtures are classified to the driver slice that can first execute them; client-side encryption is explicitly outside the roadmap pending a separate design. `spec/unified/executors.json` names every exact runnable identity and its required environment. The generator's `--check` mode prevents hand-edited or stale classification drift, while normal reports retain a row for every selected test so exclusions cannot disappear into aggregate counts.

`mongodb.unified.driver` connects the lifecycle's internal client and client, database, and collection entity factories to the public Lua driver. Its initial-data adapter uses majority writes, while its outcome adapter uses primary/local reads sorted by `_id`. Collection operation descriptors translate only declared unified arguments for reads plus `insertOne`, `insertMany`, update, replace, delete, find-and-modify, and collection `bulkWrite`; database view creation maps `viewOn` and `pipeline` through the public administration API. Find- and generic command-cursor descriptors either return a saved cursor or collect it through the common non-tailable cursor operations. They translate `timeoutMode` and `cursorType` into the public snake-case option values before validation, without implementing a tailable cursor surface. Numeric wrappers and return-document enums are converted at this boundary; iterable results are coerced to BSON arrays, and cursors are closed on exhaustion or error before matching. Write request documents become public immutable bulk models, result identifiers are reindexed to unified zero-based keys, and single/bulk results are coerced to their camel-case specification shapes. Structured bulk failures retain partial counts, exact original write-error indices, concern errors, labels, top-level command codes, and server response details for the runner's full expected-error assertions. Each client entity also owns an isolated event collector wired through the public command and pool-monitoring listeners. The SDAM listener is attached for replica-set environments and whenever the fixture observes SDAM; once attached, it retains the latest immutable topology snapshot independently of observed-event filtering, allowing `recordTopologyDescription`, `assertTopologyType`, and bounded `waitForPrimaryChange` operations to inspect actual monitor progress without exposing a test-only public client method. The collector applies observed-event, ignored-command, sensitive-command, and `configureFailPoint` filters at collection time; lifecycle assertions then match exact ordered command sequences or an explicit expected prefix when extra events are allowed. Connection-ready, checked-out, checked-in, connection-closed, pool-ready, pool-cleared, server-description-change, topology-opening, topology-description-change, and topology-closed events are normalized for exact sequence or count assertions, including minimum-pool recovery, phase-sensitive clearing, and shutdown publication. The unified `close` operation closes a client once, while entity cleanup recognizes that closed state and remains deterministic. For fixtures that request `awaitMinPoolSizeMS`, ready-connection events populate the collector's per-data-bearing-pool state, every ready pool must reach `minPoolSize`, and warm-up events are discarded before test execution. Command and reply documents reuse unified matcher semantics, while command/database names, topology-description types, and typed server/service identifier presence are checked directly. Unknown event types and fields, missing events, extra events, and reordered events fail with exact fixture paths. Runtime and URI remain injected.

`mongodb.unified.failpoints` implements only the non-targeted `failPoint` special operation; `targetedFailPoint` remains classified to the later sharded/session work. It validates the client and command, configures through that client with primary read preference and monitoring disabled, captures the server actually selected for enablement, and immediately registers a LIFO finalizer. An optional session entity is forwarded only while enabling the failpoint, allowing session-pinned setup commands without coupling cleanup to an application session. The live adapter opens a separate cleanup connection to the same URI, so a `closeConnection` failpoint cannot prevent cleanup while server targeting remains exact. ### Live compatibility matrix

`spec/compatibility/matrix.json` is the reproducible live-server inventory. It pins the official MongoDB Community Server 7.0, 8.0, and 8.2 patch images by registry digest and requires one standalone and one single-member replica-set row for each series. The validator rejects missing series/topology pairs, mutable tags, mismatched versions, duplicate rows, unknown fields, or rows that omit any required security profile.

The Linux Docker runner creates one isolated server per profile using host networking and always removes that exact container. Its plain, test-command, authentication, TLS, and authentication-plus-TLS profiles exercise the public `mongodb.client` through the normal Copas networking, LuaSec TLS, and luaossl cryptography adapters, followed by a topology-appropriate exact unified test. The runner queries the live server for its version, primary state, and replica-set name and writes those facts with the immutable image identity, active security settings, gates, and status to a versioned JSON report. Deployment failures and environment unavailability are different states: CI treats both as non-zero, while an explicit local diagnostic option may retain unavailable Docker as an environment skip. No compatibility orchestration code enters the driver or bypasses its runtime adapter boundaries.

CI expands this inventory into six required live jobs and uploads each report. The existing Linux and macOS jobs retain the full portable, loopback, installed-server, quality, packaging, and strict roadmap gates; the live Docker matrix adds advertised-version and topology evidence without replacing those jobs.

### Quality gates

The source-coverage gate is a diagnostic ratchet, not normative evidence. Busted runs the unit and deterministic integration suites with sorted files, sorted tests, and seed 1 under LuaCov 0.17. `spec/quality/coverage_gate.py` parses the source-only summary, verifies its totals, and compares exact covered/active ratios for every `src/mongodb` file and for the aggregate against the checked-in baseline. Missing files, new unbaselined files, malformed reports, and lower ratios fail. Baseline updates are explicit generated diffs; normal `make test-quality` never rewrites them.

The owned-resource audit composes the real client-handle, cursor, session-manager, topology-monitor, connection-pool, transport, and fake-runtime boundaries behind a small test-only activity counter. It establishes one active pool, cursor, session, monitor, pooled connection, and socket, then requires client closure and queued teardown to return every count to zero. The same invariant is exercised when both `killCursors` and `endSessions` return operational errors, which are deliberately ignored only after their local cursor and session ownership has been released.

`spec/quality/stress.lua` uses a local Park–Miller generator and the injected fake runtime to replay cancellation timing, successful and failed connection establishment, checkout/check-in, interrupting and non-interrupting pool clears, stale application errors versus fresh monitor state, retryable and terminal errors, callback abort cleanup, transient transaction retries, and unknown commit results. Every checked-in seed runs every boundary four times. The CLI accepts one explicit seed or `MONGODB_STRESS_SEED`, and retains failures with the seed, iteration count, Lua version, and structured diagnostic under `build/quality`. The harness owns no network, TLS, cryptography, clock, or scheduler implementation.

### Normative conformance ledger

`spec/conformance/ledger.json` is the cross-format source of truth above individual runners. Its generated inventory fingerprints all JSON and YAML files below every pinned specification `tests` tree and assigns stable identities to canonical JSON cases. It understands unified test arrays, unified schema meta-fixtures, BSON corpus categories, legacy list suites, SDAM phase suites, and singleton selection, CMAP, DNS, and related fixtures. Equivalent YAML files remain independently fingerprinted while JSON supplies the executable case identity.

Every case records the exact specification commit, source suite and format, content fingerprint, runner or explicitly pending runner, required environment, milestone scope, status, last execution command, and roadmap activity. Passing entries must name an implemented runner and evidence; unsupported entries must be owned by an incomplete activity. Generation fails on an unknown suite, and validation fails on added, removed, or changed files or cases, malformed records, missing runners or owners, and deferrals assigned to completed activities. The current ledger covers 2,966 files and 5,524 cases across 31 suites, with 3,667 passing, 1,855 explicitly deferred, and two superseded exclusions. ### Connection-string syntax

`mongodb.config.uri` owns parsing for `mongodb://` and `mongodb+srv://` connection strings without importing networking or authentication implementations. It returns an ordered seed list whose entries distinguish hostnames, IPv4 addresses, bracketed IPv6 literals, and encoded Unix socket paths; decoded credentials and authentication database; query pairs in source order; and an SRV marker retained for later resolution. An SRV authority is restricted to exactly one hostname without a port, while one- and two-label hostnames remain valid for the resolver's stricter returned-target checks. Hostnames are normalized to lowercase, ports are range checked, percent escapes and decoded UTF-8 are validated, and repeated query keys produce explicit warnings.

The URI parser intentionally preserves option values as decoded strings. `mongodb.config.options` maps those ordered strings and idiomatic programmatic tables into one immutable value. Programmatic settings take precedence over URI settings, but both paths use the same per-option validators for booleans, integers, strings, timeout/pool bounds, read and write concerns, read preference modes/tags/staleness, single-threaded selection compatibility, and TLS policy. SRV configuration adds a non-negative `srv_max_hosts`, an RFC 6335 service name extended to the DNS label limit, and static `load_balanced` conflict validation. These options are rejected on non-SRV URIs; positive `srvMaxHosts` conflicts with `replicaSet` and `loadBalanced=true`; `directConnection=true` conflicts with every SRV URI; and TLS defaults on only when an SRV parse context has no explicit URI or programmatic TLS value. Stable API is an immutable nested value, requires version `"1"`, and preserves explicitly supplied strict and deprecation flags. A separate syntax-level validation rejects `directConnection=true` with more than one seed before runtime selection.

URI inputs follow the normative warning policy: unknown keys, invalid non-security values, empty typed values, deprecated aliases, and undefined duplicates are ignored or resolved with returned warnings. An explicitly empty `authSource` is the authentication specification's hard-error exception. Repeated read-preference tag sets and equivalent `tls`/`ssl` aliases are the specified no-warning exceptions. Programmatic input is strict, so unsupported keys and invalid values return structured `configuration` errors. Conflicting TLS options remain hard errors even in a URI. The option layer never includes supplied values in its error or warning text, which keeps certificate passwords and other secrets out of diagnostics. `mongodb.discovery.dns` turns an SRV parse result into the initial seedlist before the client constructs any MongoDB transport. It validates every SRV target against the URI hostname's parent domain, preserves the minimum TTL for later polling, samples `srvMaxHosts` with runtime entropy, concatenates the character strings from at most one TXT record, admits only `authSource`, `replicaSet`, and `loadBalanced` TXT defaults, and applies explicit URI and programmatic settings above those defaults. Failed or empty SRV resolution and failed or invalid TXT resolution return structured configuration errors without opening a MongoDB socket. Other advanced post-v1 URI options remain parsed as syntax but are not exposed as accepted v1 programmatic configuration.

Normalized defaults follow the specifications: 100-entry maximum and zero-entry minimum pools, two concurrent connections, 10-second connection and heartbeat intervals, 30-second server selection, 15-millisecond local threshold, primary read preference, retryable reads/writes enabled, and TLS disabled unless explicitly selected or implied by a TLS-specific setting. A legacy URI `wTimeoutMS` creates a default acknowledged write concern even when `w` is absent; CRUD, collection bulk-write, and administration commands translate that public option to the server's `wtimeout` field, while an active CSOT context removes it in favor of the shared `timeoutMS` budget. Downstream pool, SDAM, selection, command, retry, and timeout slices consume this value rather than re-parsing user input.

### OP_MSG framing

`mongodb.wire.op_msg` is the pure-Lua message boundary for opcode 2013. It encodes and decodes the 16-byte little-endian message header, flags, exactly one kind-0 BSON command body, and any number of uniquely named kind-1 document sequences in arbitrary section order. A deterministic request-ID generator assigns positive signed 32-bit IDs and wraps without using platform randomness; response decoding may require an exact `responseTo` match before exposing the body.

The codec rejects checksum-bearing messages because CRC-32C support is intentionally absent, rejects unknown required flag bits and response-only misuse, and ignores unknown optional high bits as the specification requires. Declared frame/section/BSON lengths are checked before slicing or decoding, and negotiated `maxMessageSizeBytes` and `maxBsonObjectSize` limits are enforced on both paths. The size-accounting API uses the same encoding preparation as the wire writer, so later bulk batching can make decisions without maintaining a second overhead formula.

### Hello and single-connection commands

`mongodb.handshake.metadata` builds one immutable baseline client document when a public client is constructed. The driver name and version are fixed by the package, the normalized application name is optional and limited to 128 bytes, and the required OS type falls back to `unknown`; non-empty OS name, architecture, version, and platform facts are copied from the optional runtime metadata boundary. That boundary also supplies snapshots of relevant environment variables and root-filesystem presence. AWS Lambda, Azure Functions, Google Cloud Functions, and Vercel signals select the normative fixed `env.name`; Vercel takes precedence only over AWS, while every other ambiguous provider combination omits FaaS fields. Optional region and int32 memory/timeout facts are copied only when valid. Docker and Kubernetes facts form an independent container document and can coexist with FaaS metadata. The default Copas adapter discovers these facts once, while injected runtime facts make tests and embedded runtimes deterministic. The builder measures the complete encoded BSON document and, only while it exceeds 512 bytes, cumulatively reduces environment metadata to `env.name`, reduces OS metadata to `os.type`, removes `env`, and then truncates or removes `platform` without splitting UTF-8. If wrapper suffixes still exceed the limit, their version and name suffixes are truncated while the fixed Lua driver identity remains intact. Application and OS type also remain unchanged. The client snapshots runtime facts and the initial wrapper tuple before opening a socket. Each later `append_metadata` call validates one case-sensitive name/version/platform tuple, treats empty optional strings as unset, rejects the `|` delimiter, and ignores exact duplicates. A unique tuple atomically replaces the current bounded metadata snapshot used by future monitor, RTT, pooled application, reconnect, and discovered-member connections; established sockets retain their original immutable document, and an update alone creates or closes no connection.

`mongodb.command.executor` owns the protocol lifecycle on one exact-I/O transport connection. Its first handshake uses OP_MSG legacy `ismaster` with `helloOk: true`, unless Stable API requires modern `hello`; every hello carries the string-valued backpressure version, while only the initial hello carries the immutable client metadata supplied by the client boundary. A successful legacy negotiation permanently switches later hello requests to the modern command without resending handshake arguments. Awaitable monitoring hello requests set `exhaustAllowed`; the executor consumes each chained `moreToCome` response using the preceding server message identifier and sends a new request only after the stream ends. Other commands still reject unexpected streaming replies. The executor records the reply's BSON/message/batch limits and uses the negotiated per-connection values for later encoding and framed reads.

Commands are copied from the caller's ordered BSON document, preserving the command name as the first field. Stable API fields and the `$db` global argument are appended to the copy, so caller state is never mutated. Request IDs are correlated before a reply is exposed; I/O failures, malformed frames, invalid `ok` fields, and unexpected streaming replies close the connection. An `ok: 0` reply remains a server operation failure without closing the connection and retains its numeric code, code name, labels, timeout/retryability classification, server address, and immutable BSON response details.

`mongodb.command.hello` is the immutable per-connection capability model. It validates and supplies defaults for negotiated wire, BSON, message, batch, and logical-session fields and exposes the server's basic readability/writability shape for later SDAM work. It does not select servers, pool connections, authenticate, or import runtime-specific networking; those responsibilities remain in their dedicated layers.

### Authentication

`mongodb.config.credentials` converts the parsed URI and normalized options into one immutable credential before the client opens a MongoDB socket. A username/password delimiter selects authentication; a database path or `authSource` alone does not. Default, SCRAM-SHA-1, SCRAM-SHA-256, and PLAIN credentials require both a non-empty username and a supplied password and reject mechanism properties. SCRAM chooses an explicit `authSource`, then the URI database, then `admin`; PLAIN chooses an explicit source, then the URI database, then `$external`. MONGODB-X509 accepts an optional certificate subject as its username, rejects passwords and mechanism properties, and always uses `$external` regardless of the URI database. MONGODB-AWS creates a `$external` credential shell only when the URI supplies no access key, secret key, or session token; ordered provider slices resolve its actual credentials at authentication time. This follows DRIVERS-3131, so the two retained legacy fixtures that still expect explicit AWS URI credentials are executed and recorded as superseded exclusions instead of being made to pass through hostname-dependent behavior. Invalid combinations return value-style configuration errors containing only field names and fixed mechanism text. The same credential identity is reused by every application connection so mechanism caches remain effective, while monitor and RTT connections continue without credentials.

MONGODB-OIDC built-in environments also normalize to an immutable `$external` credential shell without a password. `ENVIRONMENT` must select `test`, `azure`, `gcp`, or `k8s`; the test environment rejects a username, Azure and GCP require a non-empty `TOKEN_RESOURCE`, and test and Kubernetes reject that property. Programmatic configuration may select a function-valued `OIDC_CALLBACK` machine identity or `OIDC_HUMAN_CALLBACK` human identity instead, but an environment and the two callback kinds are mutually exclusive. `TOKEN_RESOURCE` remains limited to Azure and GCP. A human callback receives either a copied custom `ALLOWED_HOSTS` dense string list or the immutable normative MongoDB service-domain and loopback defaults; machine callbacks and built-in environments reject that property.

`mongodb.auth.oidc` owns this mechanism-specific normalization, while the general option layer admits callback functions and allowed-host tables only from programmatic input. The normalized credential receives copied immutable mechanism properties rather than retaining mutable caller or parser state. URI configuration continues to accept only the environment and token-resource strings: callback and allowed-host material is rejected without rendering its value, colons remain valid inside a token resource, and comma-bearing resources use the programmatic mechanism-property table because comma separates URI properties. Callback functions and token-resource contents likewise never enter structured configuration diagnostics.

Machine authentication invokes the configured callback with an immutable version-one context containing the normalized username, cancellation token, absolute deadline, and remaining timeout. Its callback window is capped at 60 seconds and shortened by an earlier caller deadline. A non-empty access token is encoded as the one-step `JwtStepRequest` payload for a single `$external` `saslStart`; callback failures, malformed callback results, command failures, and malformed SASL replies become credential-free structured authentication errors. The exact pinned OIDC read and write cases run through a deterministic loopback server without exposing the token.

The immutable credential identity owns one client access-token cache, while each command executor records the exact opaque token generation used on that connection. A cached token avoids another callback across connections. Server authentication code 18 invalidates the client token only when that connection still refers to the current generation; a stale connection therefore cannot discard a newer token even when their strings are equal. A cached-token rejection fetches or observes one replacement and retries authentication once, while a newly fetched rejection is returned without another callback. Other failures retain the cache. The optional callback expiry duration remains validated but, as required by the current specification, is advisory and does not evict a cached token. Callback serialization and the 100-millisecond start interval remain isolated in `AUTH-026`; no cache coordination is held across a server command.

`mongodb.auth` dispatches the immutable credential after hello. An explicit mechanism bypasses default SCRAM negotiation. `mongodb.auth.plain` sends one RFC 4616 initial response containing an empty authorization identity, username, and password to the selected source with `autoAuthorize: 1`; it requires the server to complete that SASL exchange in its first response. `mongodb.auth.x509` sends one `authenticate` command to `$external`; it includes `user` only when the application supplied a certificate subject. Command failures and malformed replies become credential-free structured authentication errors. Neither mechanism performs runtime-specific work: deployments are expected to protect PLAIN with TLS, while X.509 client certificate and private-key loading stays within the TLS runtime adapter.

`mongodb.auth.aws` accepts only an internally resolved access key, secret key, and optional session token, then runs the two-command MONGODB-AWS SASL exchange on `$external`. Its first message uses exactly 32 bytes from runtime entropy and advertises no channel binding. The server challenge must contain a 64-byte nonce beginning with those client bytes and an STS host with the normative length and label shape. The module derives the STS region, formats the runtime wall clock as UTC without consulting process time, and builds the required SigV4 canonical request using only runtime SHA-256 and HMAC-SHA-256. The secret key participates only in adapter-backed HMAC derivation; it is absent from SASL payloads and structured errors. A temporary session token is both signed and returned in the required second payload, whose command-monitoring representation remains covered by the shared SASL redaction policy.

`mongodb.auth.aws_credentials` begins the provider chain by dynamically reading `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and optional `AWS_SESSION_TOKEN` through `runtime.environment` immediately before each uncached authentication. The Copas adapter delegates that capability to the process environment, while the fake owns a mutable isolated map; core authentication never calls `os.getenv`. A complete pair becomes a new immutable internal credential and is not cached, so a later authorization observes refreshed Lambda-style values. An absent environment permits the next provider, while any partial or empty combination fails as a credential-free structured authentication error.

The provider chain holds at most one non-environment credential and the provider that produced it. A cached value remains authoritative over later environment changes only while its expiration is more than five minutes away; at that boundary the same provider is called to refresh it before any environment fallback. Environment credentials never enter this cache. Provider output must contain a complete access/secret pair, optional non-empty session token, and a future Unix expiration, and provider failures are converted to credential-free authentication errors. Any authentication failure invalidates the cache only when the failed credential is the exact cached value, allowing the next authorization to fetch a replacement without affecting environment or unrelated authentication state.

When both `AWS_WEB_IDENTITY_TOKEN_FILE` and `AWS_ROLE_ARN` are present, `mongodb.auth.aws_web_identity` is the next provider after environment access-key credentials. It reads the token only through `runtime.file`, uses the configured session name or derives one from runtime entropy, and sends the manually encoded `AssumeRoleWithWebIdentity` request through `runtime.http` with a JSON response preference. The response must contain a complete temporary credential and a future UTC expiration before it enters the shared five-minute AWS cache. File, HTTP, timeout, cancellation, JSON, status, and expiration failures become credential-free authentication errors; paths, token contents, STS bodies, and credentials do not enter diagnostics.

When web identity is not configured and `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` is present, `mongodb.auth.aws_ecs` appends that absolute-path value only to the fixed `http://169.254.170.2` ECS link-local origin. It rejects empty, non-path, fragmented, whitespace-bearing, or control-bearing values before networking. The provider performs one adapter-backed GET with the earlier of the client deadline and a ten-second provider deadline, carries cancellation unchanged, and accepts only a successful bounded JSON response containing a complete access key, secret key, `Token`, and future UTC expiration. Valid credentials enter the same five-minute provider cache; endpoint, response, timeout, cancellation, and validation failures remain credential-free authentication errors.

The same provider accepts `AWS_CONTAINER_CREDENTIALS_FULL_URI` only when the relative URI is absent. A syntactically valid HTTPS origin may use any DNS name or IP address; plain HTTP is restricted to IPv4 and IPv6 loopback addresses plus the documented ECS and EKS link-local metadata addresses. URI credentials, fragments, invalid ports, malformed DNS/IP hosts, and non-local HTTP origins fail before the runtime HTTP adapter is called. This keeps the full-URI extension's SSRF boundary separate from response parsing and preserves the AWS relative-URI precedence rule.

Full-URI requests may carry one container `Authorization` header. `AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE` takes precedence and is read as-is through `runtime.file` with the same deadline and cancellation token as the request plus a 64 KiB limit; `AWS_CONTAINER_AUTHORIZATION_TOKEN` is consulted only when no file is configured. Empty, oversized, unreadable, or control-bearing values fail before HTTP without falling back between configured sources. Relative ECS requests ignore both authorization inputs. Provider errors retain timeout or cancellation classification while omitting token values and file paths.

When no earlier provider is configured, `mongodb.auth.aws_ec2` completes the fallback chain through the fixed EC2 Instance Metadata Service origin. It starts an IMDSv2 session with a token `PUT`, discovers the validated IAM role name with a token-authenticated `GET`, and fetches that role's temporary credential with a second token-authenticated `GET`. All three operations share the earlier of the caller deadline and one ten-second provider deadline and carry the same cancellation token. Token, role, status, size, JSON, success-code, credential, and future-expiration validation occurs before the result enters the shared five-minute cache. The provider retains only fixed endpoint paths and returns credential-free structured failures, so IMDS tokens, role names, response bodies, and credentials cannot enter diagnostics.

The default Copas runtime supplies bounded binary file reads and a small bounded HTTP/1.1 client for credential providers. HTTP resolves and connects through the existing socket adapter, wraps HTTPS through the TLS adapter with the request host as the server name, and carries the caller's absolute deadline and cancellation token through connect, write, and read. It accepts content-length, chunked, or connection-close response framing, rejects ambiguous or malformed framing, and caps response headers and bodies. Authentication and provider modules see only the runtime `file` and `http` interfaces; they never import process files, sockets, or TLS implementations.

`mongodb.auth.scram` runs SCRAM-SHA-256 and SCRAM-SHA-1 over a handshaken command executor. It generates each client nonce from 32 runtime entropy bytes, escapes the raw username for the SASL name, enforces the 4,096-iteration minimum, validates that the server nonce begins with the client nonce, and compares the expected server signature in constant time. It sends `skipEmptyExchange`, supports the older third empty exchange, and caches derived client/server keys per credential identity with mechanism, salt, and iteration guards.

SCRAM-SHA-256 prepares only the password with `mongodb.auth.saslprep`; usernames remain raw as MongoDB requires. The pure-Lua implementation maps, normalizes, prohibits, and performs bidirectional checks against checked-in Unicode 3.2 tables generated by `tools/generate_stringprep_tables.py`. SCRAM-SHA-1 preserves MongoDB's legacy behavior: neither field is prepared, and the password first becomes the lowercase MD5 hex digest of `username:mongo:password` before PBKDF2-SHA-1.

SASL commands pass through the executor so normal deadlines, cancellation, and command monitoring apply. Monitoring redacts their command/reply bodies. Authentication converts server command failures, malformed payloads, nonce/signature failures, and SASLprep rejection to credential-free structured authentication errors; it never retains response payloads, passwords, salts, proofs, or signatures in those errors.

### Command monitoring

`mongodb.monitoring` publishes immutable command-started, command-succeeded, and command-failed events synchronously around application command I/O. The executor supplies a single request ID to each correlated pair, accepts an optional operation ID for multi-command work, reports the database and connection identities, and reconstructs OP_MSG document sequences as arrays in the started event. Durations come from an injected monotonic clock capability and cover the command exchange. Initial connection handshakes are excluded from command monitoring.

Listeners are copied at monitor construction and invoked in registration order. Each callback runs behind an isolated protected call, so listener failures cannot change command results or prevent later listeners from observing the event; an optional error callback receives listener failures under the same isolation rule. Event and BSON values are immutable, preventing one listener from changing what another listener observes.

Authentication commands (`authenticate`, SASL commands, nonce/user/copydb commands) and hello commands containing `speculativeAuthenticate` publish empty command and reply documents. A shared command-security policy also replaces the public error message for a sensitive server failure and restricts its response details to `code`, `codeName`, and `errorLabels`; monitoring applies the same projection before listener dispatch. Network and other client-side failures remain inspectable because they do not contain server authentication payloads. This keeps listener and public diagnostic paths aligned without exposing credential-bearing values.

### Core API and monitored topology lifecycle

`mongodb.client` is the public constructor boundary. It separates runtime and listener capabilities from programmatic driver options, parses the URI, normalizes the initial configuration, and resolves `mongodb+srv` SRV and TXT inputs before validating the merged result, constructing credentials, or opening a MongoDB socket. Resolved SRV seedlists enter the monitored topology path; ordinary URIs without `replicaSet` retain the direct single-seed lifecycle unless a positive `minPoolSize` or an SDAM listener requires a monitored topology and its connection pool. An implicitly monitored standalone begins as Unknown and becomes Single after its first successful hello; direct connection mode begins as Single. The topology captures that hello as immutable capability input, so a concurrent background application-connection failure cannot turn client construction into an eager checkout failure. A replica-set URI accepts multiple seeds, creates a monitored topology, and discovers the authoritative host list from hello responses. Each application connection is upgraded with normalized TLS policy, sent the client's metadata-bearing initial handshake, and authenticated before entering its server pool. Monitor connections use the same runtime/TLS transport and metadata snapshot but do not authenticate or negotiate mechanisms. An application hello requests `saslSupportedMechs` only for a default-mechanism credential; the lifecycle selects SCRAM-SHA-256 when advertised and otherwise uses the required SCRAM-SHA-1 fallback. Explicit SCRAM mechanisms bypass negotiation. Multiple ordinary seeds without `replicaSet`, Unix sockets, complete sharded deployment behavior, and load balancing remain explicit errors or post-v1 classifications.

An SRV-created topology carries only the original hostname, service name, `srvMaxHosts` bound, and latest minimum TTL into `mongodb.topology`; DNS transport remains in the runtime adapter and SRV validation/randomization remains in `mongodb.discovery.dns`. One cancellable topology task polls only while SDAM type is Unknown or Sharded. A successful scan retains unchanged server descriptions, monitors, and pools; removes disappeared addresses; and creates newly selected addresses as Unknown. A positive `srvMaxHosts` retains surviving members before randomly filling remaining capacity. Invalid returned domains are ignored, while DNS failures and empty or wholly invalid results leave the topology unchanged and temporarily use `heartbeatFrequencyMS`. Successful scans schedule from completion using the lowest valid TTL with a 60-second floor. Transition to Single, either replica-set type, or LoadBalanced cancels polling, and client close wakes and joins the polling task before closing remaining server resources.

`mongodb.api` owns immutable client, database, and collection handles whose state is kept outside the visible tables. Database names reject the server-prohibited characters except for the authentication namespace `$external`; collection names reject empty components, null bytes, invalid dots, and unsupported dollar forms. Database and collection handles inherit normalized read concern, read preference, and write concern, with validated per-handle overrides. A database runs a command through the shared executor without changing the caller's ordered BSON document. Client close is idempotent and closes the executor once; all derived database handles observe the same closed state and return a structured `client` error before I/O.

`mongodb.topology_executor` gives the existing API handles the same executor contract for replica sets. It classifies read and write commands, applies a per-operation inherited read preference when selecting a server, and adds the normative camel-cased `$readPreference` OP_MSG argument with optional tags and maximum staleness. It waits for the monitored description to yield a selectable server, checks a connection out of that server's pool, and always checks it back in. Network, protocol, timeout, and server failures feed their address and connection generation back into SDAM before the next selection. Standalone and replica-set API objects depend only on configuration, runtime, transport, command, authentication, monitoring, topology, selection, and pool interfaces; runtime-specific networking, TLS, and cryptography remain behind adapters.

### Sessions and causal consistency

`mongodb.session` owns client sessions and the server-session pool. Logical session IDs are UUID-subtype BSON documents generated from the runtime entropy adapter. Explicit sessions default to causal consistency; implicit sessions disable it. Clean, unexpired server sessions return to a LIFO pool, while dirty and expired sessions are discarded. Ending a session is idempotent, ended sessions cannot decorate commands, and a manager rejects sessions belonging to another client. Client shutdown ends active sessions, drains the pool into one `endSessions` command, ignores that cleanup command's operational result, and then closes the underlying executor.

`mongodb.session_executor` decorates the existing standalone or topology executor without importing a runtime. It copies ordered commands, attaches `lsid`, gossips the greatest client/session `$clusterTime`, preserves configured read concern, merges causal `afterClusterTime` when applicable, and advances cluster and operation times from replies. Network and protocol failures dirty the associated server session, including intermediate retry attempts. A normal command owns one implicit session; multi-batch bulk work uses one operation context, while cursors retain their context across `getMore` and `killCursors` and release it on exhaustion, explicit close, malformed replies, or command failure. Explicit sessions flow through the same CRUD, bulk, administration, command, cursor, and unified-driver option boundary.

### Explicit transactions

`mongodb.session` owns the explicit transaction state machine and transaction-number allocation. `start_transaction` merges client concerns, session defaults, and call overrides, rejects an active transaction or unacknowledged write concern, and increments the server session's transaction number exactly once. Decoration adds `startTransaction` and the transaction read concern only to the first command, attaches `autocommit: false` and the stable transaction number to every command, strips operation and handle write concerns, and preserves causal `afterClusterTime`. Size measurement includes the same wire fields without consuming the starting state. Read commands validate operation-level and transaction-level preferences independently, so a primary preference from one source cannot mask a non-primary preference from the other; violations return structured client errors before executor I/O.

Commit and abort commands reuse the decorated executor path. Empty transactions complete locally; invalid state transitions do not perform I/O; ending a session aborts an active transaction. Retryable commit and abort failures make one new attempt. Both commands also retry a sanitized authentication failure that preserves a retryable handshake-network marker, even when `retryWrites=false`; the fresh connection reuses the transaction's `lsid` and `txnNumber`, and abort enters `aborted` exactly once after cleanup succeeds. Retried and repeated commits promote `w` to `majority`, preserve journal and explicit timeout settings, and otherwise use a 10-second write-concern timeout before entering `committed`. Non-control network failures inside a transaction gain `TransientTransactionError` and cannot trigger ordinary read/write retries; uncertain commit failures gain the required `RetryableWriteError` and `UnknownTransactionCommitResult` labels. Sharded pinning and recovery tokens remain behind `ADV-005`.

`with_transaction` layers the convenient API over that explicit state machine. It invokes the callback with the session, returns the callback's first result after a successful commit, and aborts an active transaction when the callback returns or throws a structured error. `TransientTransactionError` restarts the whole transaction; `UnknownTransactionCommitResult`, except code 50, retries only commit. Without CSOT both loops share a fixed 120-second budget and whole-transaction retries sleep with bounded exponential jitter sourced from the runtime entropy adapter. With CSOT the inherited session or operation deadline replaces that budget and jitter, and abort cleanup refreshes the original timeout so cleanup receives one real command attempt. A callback that explicitly commits or aborts returns without an extra commit. The callback may run more than once, so external side effects must be idempotent.

### Client-side operation timeout

`mongodb.operation_timeout` owns coroutine-local operation context above the executor stack. Public client, database, collection, cursor, and session entry points establish or resume a context containing the normalized timeout and one absolute monotonic deadline. Nested work clamps to an existing finite deadline; explicit zero establishes an infinite CSOT context. The context is restored after every protected call, so concurrent coroutines cannot leak budgets into monitors or unrelated operations.

Topology selection, pool checkout, connection establishment, TLS, authentication, command writes, and aggregate command reads all consume the same absolute deadline through their existing runtime interfaces. Under CSOT, `socketTimeoutMS` and `waitQueueTimeoutMS` do not create shorter per-layer budgets. The command boundary removes legacy write-concern timeout fields and omits `writeConcern` when no fields remain, subtracts the minimum of the latest ten monitor RTT samples after at least two samples, and appends an exact integer `maxTimeMS`; an exhausted RTT-adjusted budget fails before a write. Hello and background monitoring never receive a derived command limit. GetMore retains the client deadline but never receives derived `maxTimeMS`.

The retry executor retains its historical single retry without CSOT and makes eligible attempts until the shared CSOT deadline expires. Without a CSOT context, expiry of the per-attempt socket deadline is retryable once as a legacy transport timeout; an active CSOT timeout remains terminal at the shared deadline. Socket/external timeout errors and server code 50 are converted at the public operation boundary to a distinct timeout error whose cause is the original structured error. Pool checkout expiry is returned without feeding an application error into SDAM, so a wait-queue timeout cannot clear the pool. Runtime-specific socket, TLS, clock, cancellation, and cryptographic behavior remains behind adapters.

Cursor lifetime mode captures the initial context across getMore and allows buffered documents to be returned after expiry. Iteration mode refreshes a new deadline per `next`, omits server `maxTimeMS` for both the initial cursor command and getMore, and is rejected without an effective timeout or for `$out`/`$merge`. Explicit close refreshes the cursor timeout for killCursors even after a timed-out getMore and honors a close-specific override. Sessions inherit or override the client timeout; operation overrides take precedence, and convenient transaction callbacks cannot introduce a new nested timeout.

`mongodb.socket_timeout_executor` derives a fresh per-attempt socket deadline from the injected runtime clock only when CSOT is inactive and passes it only to the command connection's read/write operations. A first timeout therefore neither consumes nor extends the next attempt's configured `socketTimeoutMS` budget. Server selection retains its independent legacy deadline. Timed-out connections are discarded through the topology/pool boundary, allowing a retry, transaction-control retry, or later repeated commit to select a fresh connection without importing runtime-specific networking into higher layers.

### Retryable reads

`mongodb.retry_executor` sits beneath session decoration and above standalone or topology execution. Eligible `aggregate`, `find`, `findOne`, count, distinct, and database, collection, or index enumeration commands make at most one retry for a retryable server code or label, a network failure, or a legacy socket timeout. The second attempt reuses the exact decorated command and operation identifier, so its logical session and monitoring correlation remain stable while receiving a fresh transport deadline. Aggregate pipelines ending in `$out` or `$merge`, generic commands, and cursor continuation commands are not marked retryable. The normalized `retryReads` setting disables retry orchestration without changing command construction.

Each attempt uses the operation's existing deadline and performs fresh topology selection or, for a direct standalone, reconnects and repeats hello and authentication after a connection failure. A `SystemOverloadedError` initially deprioritizes the previous server during reselection, while the selector retains its normative fallback when no alternative exists. If the second attempt cannot begin because selection, topology, or pool checkout fails, the first operation error is returned; otherwise the second attempt's result is final. Reconnection remains composed from the existing transport, TLS, hello, authentication, and runtime adapters.

Failures from authentication commands are sanitized without retaining server payloads or credentials, but preserve labels, server identity, timeout state, and numeric codes. A network failure in that sanitizer is explicitly retryable, while `ShutdownInProgress` remains recognizable as code 91. An eligible read can therefore recover after either failure while establishing an application connection. A failed handshake publishes checkout lifecycle events but no application command event; the successful retry publishes the read command with the logical operation's stable monitoring identifier.

Eligible acknowledged inserts, single updates/replacements/deletes, find-and-modify operations, and homogeneous eligible bulk batches use the same executor for retryable writes. The session decorator increments the pooled server session's 64-bit `txnNumber` once before a logical write and therefore reuses it with the same `lsid` and operation identifier on the second attempt. Each eligible bulk command receives its own transaction number; multi-update/delete batches, generic commands, aggregate write stages, unacknowledged writes, standalone servers, and clients with `retryWrites=false` omit it and execute once. Network failures, legacy socket timeouts, and sanitized authentication failures that retain a retryable network marker or handshake code gain the required `RetryableWriteError` label. Collection bulk batching remains local and uses cached hello limits with an OP_MSG allowance of up to 1,000 bytes, bounded by the advertised message-to-BSON headroom, for database, session, transaction, and other operation-agnostic fields. Sizing therefore never introduces a separate observable checkout before the write attempt. Retryable write-concern responses participate in retry selection, and final-error precedence retains the most recent error that proves a write attempt occurred.

### Single-document CRUD

`mongodb.crud` builds single-document insert and find commands from collection state without importing a runtime-specific module. Insert prepends a lazily generated ObjectId only when `_id` is absent, leaving the caller's immutable BSON document unchanged. The command carries inherited write concern plus supported insert options; `w: 0` uses OP_MSG `moreToCome`, publishes no synthetic command-success event, and returns an unacknowledged immutable result. Acknowledged replies are inspected for both `writeErrors` and `writeConcernError`; structured `write` errors retain the numeric code, labels, complete immutable response, operation index, and unparsed `errInfo`.

`find_one` accepts either an ordered filter or a scalar `_id`, maps validated options to their command names, and always appends `limit: 1` and `singleBatch: true` without a batch size. It returns the first document from `cursor.firstBatch`, returns `nil` when that batch is empty, and treats malformed cursor replies as protocol errors. Raw-data options are emitted only at the negotiated MongoDB 8.2 wire version. Tailable, awaitable, and exhaust cursor modes remain outside this slice.

### Find cursor lifecycle

`mongodb.cursor` owns immutable, coroutine-aware state for one server cursor: the current cursor identifier, selected server address, buffered batch, position, retrieved count, limit, batch size, inherited comment, and command context. `collection:find` executes the initial command and validates `cursor.firstBatch`; `cursor:next` consumes buffered documents before issuing `getMore`, validates `cursor.nextBatch`, and updates the opaque 64-bit cursor identifier. Generic command cursors retain their initially selected server address for every `getMore` and `killCursors`. A positive limit caps getMore batch size to the remaining document count. When the requested limit and initial batch size are equal, the initial command sends `batchSize = limit + 1` as required to avoid an otherwise unnecessary open cursor.

Zero-id exhaustion closes the cursor locally, and an implicit session is returned as soon as the server reports that zero identifier even when documents remain buffered. A timed-out getMore retains its live identifier and implicit session so explicit close can still issue `killCursors`; network and malformed-response failures close local state immediately. Explicit close refreshes the cursor's inherited timeout after lifetime expiry, honors an operation override, and then deterministically releases the implicit session. Each client keeps a weak registry of live cursors and closes them before its executor connection, so early client shutdown also performs server cleanup. Cleanup is never initiated from a garbage-collection finalizer because runtime command I/O may yield; applications stop early with `cursor:close`, while normal exhaustion and `client:close` are deterministic.

### Update, replace, and delete

`mongodb.crud` maps `update_one`, `update_many`, and `replace_one` to distinct update command models. Atomic update documents must be non-empty and begin with a `$` field; update pipelines must be non-empty BSON arrays containing only documents. Replacement documents use the inverse validation and may not begin with an atomic modifier. The model carries `multi`, `upsert`, array filters, collation, hint, and single-update sort as applicable, while command-level validation, comments, `let`, raw-data, and inherited write concern remain ordered outside the model.

`delete_one` and `delete_many` differ at the command boundary only by their normative limits of one and zero. Acknowledged mutation results expose immutable matched, modified, upserted, or deleted counts, and replacement/update upserts preserve the server-returned identifier. Unacknowledged mutations use OP_MSG `moreToCome`, expose no unavailable counts, and reject collation, array-filter, hint, or sort combinations that their negotiated wire version cannot safely execute. These command builders depend only on BSON and the executor interface; they introduce no runtime-specific networking behavior.

### Core collection read and modify operations

Collection aggregation validates an ordered BSON array of document stages and inspects only the final stage to identify `$out` or `$merge`. Read pipelines inherit read concern. Write pipelines inherit write concern, add read concern on MongoDB 4.2 and newer, carry the inherited read preference through replica-set selection and OP_MSG command construction, ignore an initial batch size, and synthesize an exhausted cursor after an unacknowledged OP_MSG send. All other aggregate results enter the existing cursor model, so batch size, getMore comment and maximum await time, explicit kill, and client-close cleanup have one implementation.

`count_documents` builds the normative `$match`, optional `$skip` and `$limit`, and `$group` pipeline and parses its single cursor result, treating an empty batch as zero. `estimated_document_count` intentionally uses the metadata-based `count` command, while `distinct` validates and returns the server's BSON values array. These read helpers inherit read concern and use the same deadline/cancellation executor boundary as find. Their internal `raw_data` option, shared by list-collection and create/list/drop-index administration, is validated as a boolean and appended as `rawData` only when the selected server advertises wire version 27 or newer (MongoDB 8.2); older servers omit it without changing the operation result shape.

The three find-and-modify helpers share one ordered `findAndModify` builder but retain update-versus-replacement validation. Delete sets `remove`; update and replacement set `update`, optional upsert, and a `new` boolean derived from the public `before`/`after` choice. Projection maps to the wire-level `fields` name. Array-filter and hint constraints are checked before unacknowledged I/O, write and write-concern errors reuse the structured write-error path, and BSON null results map to Lua `nil`.

### Collection bulk writes

`mongodb.bulk` defines immutable insert, update, replacement, and delete models shared by `collection:bulk_write`; `insert_many` builds the same insert models internally. Ordered execution preserves adjacent command-kind runs and stops on the first write error. Unordered execution groups compatible models while retaining each model's original 1-based request index for upsert identifiers and structured write errors. Every command in one call carries the same operation identifier.

Batch construction observes `maxWriteBatchSize`, then encodes each candidate `documents`, `updates`, or `deletes` sequence locally against the cached hello limits. Its OP_MSG allowance is capped at 1,000 bytes and bounded by the advertised message-to-BSON headroom, so database, session, transaction, and other operation-agnostic fields fit without a separate connection checkout. Individual insert and replacement documents are also checked against `maxBsonObjectSize` where an unacknowledged server cannot report the violation. Networking, TLS, and cryptography remain behind their existing runtime adapters.

Acknowledged responses merge counts, upsert identifiers, write errors, write-concern errors, labels, and raw response documents into immutable results or structured partial-result errors. Unacknowledged requests use `moreToCome`; ordered multi-batch requests acknowledge intermediate batches so the driver can preserve stop-on-error semantics before sending the final unacknowledged batch.

### Database, collection, and index administration

`database:run_command` accepts a non-empty command name or ordered BSON document and returns the server reply through the shared operation/session executor. Generic commands are selection reads: they default to primary independently of inherited client or database preferences, while an explicit operation read preference is normalized and passed through the topology selector. The command document itself receives no inherited read concern or write concern; explicit command fields remain untouched. The unified adapter validates `commandName`, orders that field first when fixtures provide a differently ordered command document, and translates the unified read-preference document at the adapter boundary. Network, TLS, and cryptographic behavior remain behind the existing runtime and command-executor adapters.

`database:run_cursor_command` applies that same initial-command selection contract but requires a cursor response immediately and returns the shared public cursor model. The response namespace supplies the collection name; a missing cursor, malformed namespace, identifier, or first batch is a structured protocol failure. Optional `batch_size`, `max_await_time_ms`, and `comment` values decorate later getMore commands without mutating the caller's initial command. A supplied `timeout_mode` requires `timeout_ms`; `cursor_type` is accepted only as a validation input, and tailable command cursors are rejected before I/O, with `cursor_lifetime` explicitly incompatible. The first selected address is captured below the retry/session layers and pins every continuation and explicit kill to that server. One implicit session is retained across the initial command and getMore sequence, while an explicit session remains caller-owned. Sharded metadata commands, load-balanced connection pinning, and tailable command cursors remain post-v1; CMAP assertions and timeout-close cleanup run through exact release conformance cases.

`mongodb.admin` builds list, create, modify, and drop commands for databases, collections, and indexes without importing any runtime provider. The public client, database, and collection handles supply their inherited concerns, negotiated wire version, executor, and shared cursor registry. Collection creation preserves clustered-index and time-series documents plus time-series expiration in the ordered command. Collection modification exposes validator updates and index constraint transitions through `database:modify_collection`; command failures preserve root-level server details such as constraint violations and validation `errInfo`. Write commands apply inherited write concern and retain write-concern response details; collection and index drops treat namespace-not-found as an idempotent success.

Database enumeration wraps the command's returned array in an exhausted local command cursor. Collection and index enumeration use the server cursor namespace to construct getMore and killCursors commands, then share the existing cursor lifecycle and client-close cleanup. A listCollections comment is not repeated because the server inherits it, while listIndexes explicitly carries its comment onto getMore as required by the index-management specification.

Immutable index models retain ordered key documents, validate supported directions and option types locally, and generate deterministic key-direction names. `create_index` delegates to the same createIndexes path as multi-index creation. Create, list, and drop operations inherit or override one CSOT deadline, including `list_index_names` cursor collection and the all-index `drop_indexes` adapter. The boundary rejects `commit_quorum` before MongoDB 4.4 and gates internal raw-data fields on the MongoDB 8.2 wire version; all network behavior remains behind the command executor and runtime adapters.

### SDAM descriptions and transitions

`mongodb.sdam` is the side-effect-free phase-one SDAM core. It parses modern `hello` and legacy `ismaster` replies into immutable server descriptions, including replica-set membership, topology versions, generations, wire compatibility, election metadata, session timeout, tags, and server limits. Topology updates return new immutable descriptions and leave every prior snapshot unchanged, so monitor scheduling and selection can publish consistent views without sharing mutable transition state.

The transition table covers Single, Unknown, Sharded, ReplicaSetNoPrimary, and ReplicaSetWithPrimary descriptions. It discovers and removes replica-set members, rejects mismatched set names and stale primaries, invalidates an older primary when a newer one appears, preserves monotonic election metadata, ignores stale topology versions and connection generations, and computes topology-wide wire compatibility and logical-session timeout. The v1 client range is wire version 21 through 27, matching MongoDB 7.0 through 8.2.

This module performs no I/O and imports no runtime provider. `mongodb.topology` owns the mutable orchestration layer above it: one independent monitor task and dedicated unauthenticated connection per server, awaitable hello with the last topologyVersion when supported, a separate RTT connection, topology-change signaling, pool ready/clear transitions, and heartbeat plus SDAM event publication. Once an initial check discovers topologyVersion, streaming mode begins its first awaitable hello immediately instead of sleeping for heartbeatFrequencyMS; each successful streamed reply starts the next receive without a polling delay. Streaming mode records the initial monitor handshake as its first RTT sample, then schedules RTT probes independently of awaited hello after each heartbeat interval; polling mode never starts the extra RTT task. RTT probes update only average and minimum RTT fields without publishing monitoring events, while a main monitor failure resets the sample window. An application error that marks a server Unknown cancels any in-flight awaitable check and requests a minimum-frequency rescan, ensuring recovery uses a non-awaitable handshake that restores RTT before selection resumes. Selection failure requests an immediate scan while respecting the minimum heartbeat frequency. Discovered members receive monitors and pools; removed members are closed. Opening publishes the seeded description from an empty Unknown snapshot. Shutdown marks the topology closed, cancels shared monitor work, replaces the live snapshot with an immutable empty Unknown description, and publishes that final topology-description change. It then cancels individual monitor I/O and sleeps, waits for the tasks to finish, closes monitor connections and pools, publishes server-close events before topology-close, and ignores late monitor results. `TopologyClosed` remains the last SDAM event.

### Server selection

`mongodb.selection` composes immutable read preferences with an immutable SDAM topology snapshot. It applies topology and operation rules first, retries without address deprioritization when the preferred set is empty, then filters replica-set reads by max staleness and the first matching tag set. An optional application selector runs before the final `localThresholdMS` latency window. Selection from that window uses the power-of-two choice rule against caller-supplied operation counts supplied by each connection pool.

Max staleness is validated against both the 90-second minimum and `heartbeatFrequencyMS + 10 seconds`. Estimates use the normative with-primary and no-primary formulas over hello `lastWriteDate` and local `lastUpdateTime` values. RTT samples use the specified 0.2/0.8 exponentially weighted moving average. Invalid preferences and unavailable RTT data return structured configuration errors, while an exhausted selection returns a structured timeout whose message and `topology` field describe the final immutable snapshot.

The selection layer is pure and never sleeps or performs I/O. It evaluates the snapshot supplied by its caller; `mongodb.topology` owns monitor wakeups and topology-change waits and passes the final snapshot into timeout errors. The unit gate runs all 88 pinned JSON server-selection filtering fixtures, 32 max-staleness fixtures, 7 RTT vectors, and 8 operation-count choice distributions. Their YAML files duplicate the same cases. The five structured server-selection logging fixtures are explicitly deferred to post-v1 `ADV-009`, which owns logging and telemetry.

### Connection pools and CMAP

`mongodb.pool` owns one coroutine-safe pool per server. It starts paused, enters the ready state explicitly, assigns monotonically increasing connection identifiers, and maintains distinct pending, available, and checked-out sets. A FIFO wait queue enforces `maxPoolSize` and `maxConnecting`; its operation count includes queued, connecting, and checked-out work so server selection observes actual load. Cancellation, timeout, setup failure, check-in, clear, and close each release their owned capacity exactly once.

Connection establishment is an injected adapter that returns an already connected, TLS-upgraded, handshaken, and authenticated resource or a structured error. The pool itself imports only the runtime contract and structured-error layer. It therefore contains no socket, TLS, cryptography, hello, or authentication implementation. Network and timeout failures during setup receive the backpressure labels required by the pooling specification, except authentication and explicitly exempt failures.

Generation changes make available connections stale, clear queued work, and optionally interrupt pending and checked-out connections. Maintenance prunes idle or closed resources and restores `minPoolSize`; a failed background establishment releases its pending and total capacity and delegates the pool-clear decision to SDAM. Authentication failures clear and pause the pool until a successful monitor check readies it, while initial-handshake network failures carrying `SystemOverloadedError` leave the pool ready and schedule a delayed population attempt. The monitored topology connects pool readiness and clearing to server-description and application-error transitions. Pool and connection lifecycle events are immutable and published in normative order. Load-balanced service-specific generations remain post-v1 with load balancing.

The unit gate executes all 26 pinned JSON CMAP unit fixtures. The integration gate executes all seven pinned establishment, cancellation, and `maxConnecting` timing fixtures against an injected asynchronous connection adapter; their YAML counterparts duplicate the same cases. Replica-set application connections and standalone clients with a positive minimum use those pools. The exact standalone SDAM fixture proves that a transient code-91 handshake failure clears the pool without leaking capacity, marks the server Unknown, and permits monitor readiness to replenish the minimum afterward. Handshake metadata conformance covers baseline transmission, environment discovery, bounded-size reduction, wrapper updates, and the pinned unified metadata lifecycle fixture. The two JSON CMAP logging fixtures are deferred to post-v1 `ADV-009`, which owns logging and telemetry.

## Planned layers

1. **Values:** ordered containers and JSON, every BSON wire value, exact numeric handling, configurable codec limits, and canonical/relaxed Extended JSON are implemented.
2. **Runtime:** coroutine scheduling, monotonic time, cancellation/deadlines, locks, exact socket I/O, TLS, and crypto capabilities.
3. **Protocol:** message framing, OP_MSG, command encoding, authentication conversations, and reply/error conversion.
4. **Topology:** immutable server/topology descriptions, SDAM transitions, monitoring, selection, connection pools, and wait queues.
5. **Execution:** command lifecycle, sessions, retries, transactions, CSOT, monitoring, and cursor cleanup.
6. **API:** clients, databases, collections, cursors, concerns, preferences, CRUD, bulk, and administration.
7. **Conformance:** unified entities, requirements, event matching, fake services, schema validation, fixture classification, and reporting.

Dependencies point downward. API objects do not call Copas, LuaSocket, LuaSec, or OpenSSL directly; they depend on runtime and protocol interfaces. The same boundary supports deterministic unit fakes.

## Command data flow

A public operation validates options, creates an operation context and deadline, selects a server, checks out a connection, applies session/transaction fields, encodes OP_MSG, performs exact deadline-aware I/O, decodes and classifies the response, emits monitoring events, updates session state, and returns a value or structured error. Cleanup is deterministic on every branch.

## Intentional exclusions

Version 1 stops at standalone and replica-set production core. Post-v1 activities cover change streams, GridFS, DNS seedlist discovery, compression, sharding, load balancing, client bulk write, additional authentication, logging, telemetry, and backpressure. Initial SRV/TXT resolution and periodic Unknown/Sharded SRV polling are implemented DNS seedlist increments. Client-side field-level/queryable encryption and GSSAPI remain outside the roadmap until separately designed.
