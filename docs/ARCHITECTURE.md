# Architecture

Status: load balancing v0.10 release-ready. This document must be updated in the same activity that changes an architectural contract.

## Design constraints

The production implementation targets Lua 5.4 and Lua 5.5 with 64-bit integers. Driver, BSON, wire protocol, SDAM, CMAP, selection, retry, and transaction behavior are pure Lua. A coroutine-aware runtime interface isolates clocks, cancellation, tasks, locks, environment access, sockets, TLS, entropy, hashing, HMAC, PBKDF2, and optional wire-compression providers. The supported default adapter is Copas 4.11 with LuaSocket, LuaSec, LuaRocks-provided MD5, SHA-1, and operating-system entropy modules, the driver's pure-Lua SHA-256 primitive, a required lua-zlib provider, and optional lua-csnappy and lua-zstd providers.

The top-level module enforces the Lua version and integer-width constraints at load time. The public module version, handshake driver version, release rockspec, and changelog share the load balancing release version `0.10.0`; the LuaRocks revision is `0.10.0-1`. The README intentionally keeps its LuaRocks installation command versionless. The LuaRocks package maps every production module below `src/mongodb`; its package gate builds a source rock from the current checkout, installs it in a temporary tree, removes workspace paths from Lua's module search, and exercises the documented client, BSON, runtime, bulk-model, index-model, and GridFS bucket entry points under the active supported Lua version. The six `mongodb.unified.*` modules implement specification-test infrastructure, live below `spec/support`, and are classified explicitly as test-only in `spec/module-classification.json`; they are loaded only through test search paths and are excluded from the rockspec, production architecture graph, complexity ratchet, and production coverage baseline. Busted specifications live under `spec`, and Luacheck enforces the common Lua 5.4/5.5 language subset plus project style. Its W561 report also feeds a checked cyclomatic-complexity ratchet: new production functions may score at most 40, existing higher-scoring hotspots may not increase, and any reduction must replace the baseline so the improvement is retained. Verification has three explicit compositions: `make check-fast-runtime` runs the runtime-independent and active-Lua unit, integration, static unified, architecture, generated-artifact, stress, compatibility-matrix, package-install, rockspec, and planning gates; `make check-fast` adds complexity and lint; and `make check-full` adds live unified execution and coverage. `make check` remains the full release alias. Unified fixture parsing and schema validation occur once in either composition rather than being repeated by the inventory gate. Per-commit Actions run `check-fast` on Ubuntu and macOS for Lua 5.4 and run `check-fast-runtime` on both platforms for Lua 5.5. Luacheck 1.2.0 remains on Lua 5.4 because the tool itself does not execute under Lua 5.5; it still parses every production source file as the common supported language subset. The workflow probes the oldest standalone plus newest replica-set compatibility boundaries on Lua 5.4. Complete Linux conformance and all nine compatibility rows run nightly; complete macOS conformance runs weekly, and both platforms can be requested manually for an exact commit. Superseded per-commit and full-conformance runs are canceled by workflow/ref concurrency groups. Publication is restartable without replacing immutable artifacts: an existing LuaRocks rockspec must match byte-for-byte, a missing source rock is attached only to that version, and both public artifacts must match the locally rebuilt tag artifacts before public installation and GitHub release creation proceed.

Release source rocks are constructed from the selected commit's tracked superproject tree and the byte-matching committed rockspec. The builder deliberately omits pinned reference-submodule payloads, retains the source directory layout declared by the rockspec, and rejects artifacts above 10 MiB before publication.

The public entry point is `require("mongodb")`. Modules and functions use `snake_case`; stateful public values use colon methods. Operational APIs return `value` on success or `nil, err` on failure. Structured errors have stable categories, codes, labels, causal chains, and server details. Programmer misuse and broken internal invariants may raise.

### Structured error contract

`mongodb.error` constructs readonly error values rather than an exception hierarchy. Every value has a known `category` and non-empty `message`; it may also carry a numeric MongoDB `code`, `code_name`, ordered unique `labels`, a structured `cause`, server/topology context, timeout/retryability flags, and recursively readonly `details`. Diagnostic string conversion intentionally excludes details so arbitrary server documents and secrets are not rendered accidentally.

Category, label, timeout, and retryability predicates let execution layers classify failures without parsing messages. Adding or removing a label creates a new value and preserves the original causal value. Invalid constructor fields, unknown categories/options, and attempts to mutate public values are programmer errors and raise immediately. Network, protocol, server, selection, authentication, pool, BSON, and other operational failures must construct one of these values and return it as `nil, err`.

### Runtime interface

Core modules receive one validated runtime value and never import a scheduler, socket, TLS, entropy, or crypto library directly. The interface groups capabilities by responsibility:

| Capability | Required operations |
| --- | --- |
| Clock | monotonic `now`, Unix `wall_time`, and coroutine-aware `sleep` |
| Cancellation | create tokens with idempotent cancellation and ordered listeners |
| Tasks | spawn, await, and cancel coroutine work |
| Locks | create locks with explicit acquire/release transitions |
| DNS | resolve SRV and TXT records with TTL and character-string boundaries intact |
| Sockets | connect and return sockets supporting partial read/write and idempotent close |
| TLS | wrap an established socket without leaking adapter details upward |
| Entropy | return an exact number of random bytes |
| Crypto | MD5, SHA-1/SHA-256, corresponding HMAC, and PBKDF2 variants |
| Compression | optional named providers with a wire compressor identifier and whole-message compress/decompress operations |

Deadlines are absolute values from the runtime's monotonic clock. Unix wall time is a separate capability for BSON ObjectId generation and other protocol timestamps; it is never used for elapsed-time decisions. Shared helpers derive deadlines, clamp remaining time to zero, and classify cancellation before expiration as structured operational errors. Adapter validation treats a missing function as programmer misconfiguration.

`mongodb.runtime.fake` implements the entire boundary without external dependencies. Its clock advances only under test control, tasks execute in queue order, DNS results and socket reads/partial writes consume scripts, cancellation is synchronous, TLS/entropy/crypto calls are recorded or scripted, and compression providers are injected by name. DNS scripts retain SRV targets, ports, priorities, weights, and TTLs or ordered TXT character strings and TTLs; an empty record array is a successful no-answer result. Missing fake scripts raise because they indicate a malformed test, while scripted operational failures return `nil, err`.

`mongodb.runtime.copas` implements the scheduling boundary with Copas 4.11 futures, pauses, non-reentrant locks, and LuaSocket providers. The built-in Copas and fake adapters expose an additional yield-control scheduling handoff for unified test thread entities; production driver code does not use it, so it is not required from application-supplied adapters. Copas hands execution to newly spawned work without awaiting completion, while the fake adapter advances one deterministic queued task. The adapter clamps Copas time so the driver never observes backward movement, wakes sleeping tasks on cancellation, and polls contended locks, socket waits, and DNS receives so cancellation remains bounded. `mongodb.runtime.copas_dns` discovers recursive nameservers from `resolv.conf` or accepts an injected adapter-local list, sends coroutine-safe UDP SRV/TXT queries, retries truncated answers over TCP, and normalizes wire replies without exposing provider sockets to configuration, discovery, or topology code. Query IDs come from runtime entropy; one finite query budget is shared across configured nameservers and any TCP fallback. NXDOMAIN and a successful empty answer return an empty record array, response codes return network errors, malformed replies return protocol errors, and caller deadlines or cancellation retain their existing structured categories. Its default `mongodb.runtime.openssl` compatibility module supplies cryptographically secure entropy through `lua-cryptorandom`, MD5 through `md5`, SHA-1 and HMAC-SHA-1 through `sha1`, pure-Lua SHA-256 and HMAC-SHA-256, and PBKDF2 over those HMAC primitives. The historical module name remains stable for consumers and runtime injection; it no longer requires luaossl. MD5 exists only for MongoDB's legacy SCRAM-SHA-1 password transform. Authentication applies the configured socket timeout independently to each exchange after local cryptographic work, while an explicit caller deadline remains shared across the connection attempt. Its default TLS provider is the LuaSec adapter described below. `mongodb.runtime.zlib` turns lua-zlib's streaming API into a whole-message provider with compressor id 2 and exact levels -1 through 9. `mongodb.runtime.snappy` and `mongodb.runtime.zstandard` turn lua-csnappy and lua-zstd whole-message APIs into providers with compressor ids 1 and 3. All three adapters convert binding failures to structured operational errors and keep native modules out of wire code. The Copas registry advertises each provider only when its module loads successfully; absence never prevents client startup. Configured but unavailable optional providers are omitted from the handshake and recorded in the public client's immutable warnings. Callers may inject conforming providers without changing core code.

`mongodb.run` is the standalone-program convenience boundary over that adapter. It validates that the caller supplies a function, rejects ownership when a Copas loop is already active, runs the callback in a Copas coroutine, preserves every callback return value including nil positions, and rethrows callback errors without scheduler-specific wrapping. It does not create or implicitly close clients; applications retain explicit resource lifecycles, while frameworks that already own Copas continue to call the normal client API inside their existing loop.

### Exact TCP transport

`mongodb.network.transport` owns runtime-neutral connection lifecycle and exact byte transfer. It repeatedly calls the runtime socket's partial read/write operations until the requested byte count is satisfied, checking the same absolute monotonic deadline and cancellation token before every attempt. EOF, network failure, timeout, and cancellation remain distinct structured errors. Length-prefixed frame reads validate the four-byte size before allocating or reading the remainder, and close is idempotent on every path. SOCKS5 is a terminal unsupported capability; the runtime boundary does not expose proxy negotiation, authentication, or forwarding contracts.

`mongodb.runtime.copas_socket` is the runtime-specific LuaSocket adapter. It wraps non-blocking TCP sockets with Copas, applies the remaining absolute deadline to connect/read/write waits, and bounds waits with a short poll interval when cancellation is enabled. A cancellation listener closes an in-use socket to wake a blocked read immediately, after which the adapter returns the structured cancellation error instead of the provider's closed-socket result. LuaSocket error strings are translated at this boundary and never leak scheduler or socket objects into wire, topology, or command code. Loopback integration tests exercise the real Copas scheduler and LuaSocket provider with deliberately split response writes and a cancelled blocked read.

### LuaSec TLS transport

`mongodb.runtime.luasec` converts normalized per-connection TLS policy into a LuaSec client context, while `mongodb.runtime.copas_socket` owns the runtime-specific SNI and asynchronous handshake. The core transport supplies the same absolute deadline and cancellation token used for TCP establishment; handshake polling bounds cancellation latency without resetting that deadline. A successful upgrade preserves the abstract partial read/write socket contract, so no core module imports LuaSec or sees its socket objects.

Certificate-chain and hostname verification are enabled by default. A custom CA bundle takes precedence; otherwise the adapter uses `SSL_CERT_FILE`, then common Unix CA bundle paths, with `SSL_CERT_DIR` as a directory fallback. If no trust store is available, context construction returns a structured configuration error rather than silently disabling verification. DNS connections send SNI. Hostname matching gives subject alternative names precedence over the common name, supports exact DNS names, a wildcard covering exactly one leftmost label, and canonical IPv4/IPv6 subject alternatives.

A combined client certificate/private-key PEM may be supplied with an optional decryption password. Context and handshake failures are converted to credential- and path-free structured errors. `allow_invalid_hostnames` disables only name matching; `allow_invalid_certificates` disables chain verification and therefore name matching; `insecure` disables both. LuaSec 1.3 does not expose certificate revocation, OCSP stapling, or OCSP endpoint verification through this adapter. OCSP is therefore a terminal unsupported capability: `disable_ocsp_endpoint_check` and `disable_certificate_revocation_check` document connection-string intent but do not alter behavior, and core TLS code does not add a second certificate-verification stack outside the runtime adapter. TLS compression and renegotiation are disabled where the linked OpenSSL supports those controls.

### BSON values and codec

`mongodb.bson` represents documents and arrays with explicit immutable containers. Documents retain insertion order and duplicate keys; indexed access returns the last matching key while `keys`, `entries`, and `iter` preserve every wire entry. Arrays are distinct from documents, and `bson.null` is distinct from absent Lua values. Constructors copy their input so later mutation cannot change an in-flight command.

The codec exposes only document-level `encode` and `decode` entry points; element encoding, value decoding, and their mutual recursive container traversal remain local implementation details. Element encoding validates key and sized-text frames through shared helpers, handles explicit BSON containers first, and dispatches tagged, exact-numeric, and native Lua values through local type-specific encoders. Value decoding uses the corresponding private BSON-type decoder table; each handler retains its own fixed or variable payload validation while shared readers enforce frame bounds before access. It accepts only an ordered document at its root and encodes Lua strings as BSON strings, integral numbers as the smallest signed BSON integer, non-integral numbers as doubles, and explicit wrappers for arrays, binary data, and null. Immutable tagged values represent ObjectId, signed-millisecond UTC datetime, regular expression, timestamp, JavaScript code with optional ordered scope, Symbol, DBPointer, Undefined, MinKey, and MaxKey. Binary values retain every subtype and apply the legacy subtype-2 nested length rule. Decoding produces the same unambiguous value model. Arbitrary Lua tables are rejected because neither their intended BSON type nor their iteration order is defined.

Decoded int32, int64, and double values use explicit immutable wrappers carrying both the Lua value and original little-endian bytes. Their constructors also let callers force a numeric wire type; unwrapped Lua integers still select the smallest signed representation. This preserves small int64 values, double negative zero, and NaN payload bits across a decode/encode cycle without overloading arithmetic operators.

Decimal128 is stored as its exact 16-byte Binary Integer Decimal representation. String conversion uses decimal-digit and byte-array arithmetic in Lua, applies the 34-digit half-even context's exactness, exponent, and clamping rules, and never passes through a binary float. NaN variants and non-canonical encodings retain their input BID even when their required diagnostic string is lossy. The pinned official Decimal128 corpus is the conformance source.

ObjectId generators are stateful values constructed from an injected runtime. They obtain a five-byte generator identifier and three-byte initial counter from `runtime.entropy`, read seconds from `runtime.clock.wall_time`, and increment the 24-bit counter without importing platform time or randomness into BSON code. Deterministic vectors cover the complete unsigned timestamp boundary set from `0x00000000` through `0xffffffff` and the counter rollover from `0xffffff` to zero. ObjectId, datetime, timestamp, regex, and binary values implement equality or ordering where their BSON semantics define it.

All lengths and element payloads are checked against their containing frame before reading. Invalid document, string, binary, code-scope, boolean, terminator, trailing-byte, UTF-8, and unsupported-type encodings return structured `bson` errors carrying a one-based byte offset. Codec options bound document, string, binary, and nesting sizes; the defaults are 16 MiB for each size and 100 document levels. UTF-8 validation is on by default and may be disabled explicitly for byte-preserving diagnostic work. Degenerate array keys and unordered regex flags accepted by the BSON corpus are normalized when re-encoded.

### Ordered JSON and Extended JSON

`mongodb.bson.json` parses JSON directly into the ordered BSON value model, including explicit arrays, null, and exact numeric wrappers. The recursive-descent parser validates JSON number grammar, UTF-8, escapes and surrogate pairs, trailing input, and configurable input/string/depth limits. It does not pass object pairs through an unordered Lua table.

Extended JSON conversion recognizes canonical, relaxed, and permitted degenerate representations for every BSON wire value. Parsing recursively converts document children before a local wrapper-handler map classifies the enclosing document; shared validation helpers enforce exact outer and nested wrapper fields while dedicated handlers retain type-specific construction and diagnostics. Unknown dollar-prefixed documents remain ordinary documents. Generation supports canonical and relaxed modes, preserves field order, uses canonical Base64/subtype encoding, and emits ISO-8601 UTC datetimes only where relaxed Extended JSON permits them.

BSON binary subtype 9 has a small public vector view rather than a numerical-library dependency. `mongodb.bson.vector` validates dense Lua input and emits the mandatory dtype and padding bytes followed by little-endian INT8, FLOAT32, or PACKED_BIT data. `binary:as_vector` validates the same invariants when explicitly unpacking generic binary data and returns an immutable record whose numeric data is an explicit BSON array. FLOAT32 payload lengths must be divisible by four; non-bit padding, out-of-range values, empty padded bit vectors, and non-zero ignored bits are rejected. All 22 pinned vectors execute from numeric input through canonical BSON bytes and back.

### Unified schema validation

`mongodb.unified.schema` compiles an ordered JSON Schema document into an immutable validator. The implemented draft 2019-09 subset covers the constructs exercised by unified schema 1.28: local references, object properties and required fields, additional and pattern properties, array/property bounds, primitive types, enums, constants, the version and KMS-provider patterns, and `allOf`, `oneOf`, and `not`. Schema violations return structured `configuration` errors with both a JSONPath-like document path and a JSON Pointer schema path.

The schema gate loads only fixture envelopes in Python and performs parsing and validation in Lua. Both `valid-pass` and `valid-fail` are schema-valid—the latter are reserved for later runner failures—while every file in `invalid` must be rejected. The meta-runner gate covers all 320 distinct JSON fixtures pinned with the specification checkout; equivalent YAML copies are not counted twice. A separate integration-fixture gate passes all 548 pinned JSON files through the same ordered Extended JSON parser, rejects schema versions outside the supported 1.28 line, validates each document against schema 1.28, and inventories all 2,599 contained tests.

`mongodb.unified.runner` is the execution-neutral core. Each test creates a runner with an isolated entity registry, environment facts, entity factories, per-entity-kind operation handlers, and an optional outcome reader. Entity IDs are unique and typed; missing entities, unsupported entity kinds, unsupported operations, and unknown match operators return visible `configuration` errors with document paths. This registry/dispatch boundary lets later slices connect real driver objects without teaching the runner about transports.

`mongodb.unified.lifecycle` is the test-file orchestrator around that core. It evaluates file and test `runOnRequirements` plus `skipReason` before setup, delegates `initialData` and outcome reads to one injected internal-client adapter, and creates a fresh runner and entity map for every executed test. Operations finish before registered listener/failpoint finalizers; only a successful operation phase proceeds to event and outcome assertions. An entity observer then receives the still-live isolated map before teardown. Every path—including an operation or assertion failure—runs remaining finalizers and destroys entities in reverse registration order, ending sessions, closing clients and cursors, and awaiting threads by default or through kind-specific cleanup adapters. Failures are reported per test and never stop subsequent tests. The lifecycle owns no socket, deployment, or scheduler implementation; environment facts, runtime, internal commands, entities, and operations remain injected boundaries.

Run-on requirements compare numeric version components and environment topology, authentication, serverless, server-parameter, and encryption facts. Matching implements strict nested documents, root subset matching, flexible BSON numbers, exact arrays, and every unified operator: `$$exists`, `$$type`, `$$matchesEntity`, `$$matchesHexBytes`, `$$unsetOrMatches`, `$$sessionLsid`, `$$lte`, `$$matchAsDocument`, and `$$matchAsRoot`. Hexadecimal-byte expectations compare decoded bytes with string results, session IDs are resolved through the typed entity boundary, and entity matches recursively apply normal matcher semantics. Iterable result documents retain root subset matching, while outcome documents require exact fields but ignore BSON key order. The meta gate executes all 19 dedicated upstream matcher pass/fail cases plus pinned GridFS and session operator expectations without a server.

Thread entities schedule work through the injected runtime task interface and yield control once so the target begins immediately without waiting for completion, as required by the unified format. Bounded loops record iteration and success counters as BSON entities. Unit tests use the deterministic fake runtime and fake entity/operation handlers; no runner-core test opens a network connection.

Entity operation adapters are descriptors with a handler, an explicit accepted-argument set, optional result coercion, and an optional saved-entity kind. The runner resolves `session` arguments through the typed entity registry before dispatch, rejects unknown arguments before a handler can perform I/O, ignores only structured operational failures when requested, and refuses missing or unsupported saved results. BSON results are inferred; find cursors, command cursors, and change streams require an explicit result kind.

Expected-error processing asserts client origin, timeout status, case-insensitive message and code-name matching, numeric codes, included and omitted labels, exact write-error indices, ordered write-concern errors, root-level server responses, and partial results. Unknown expectation fields and unstructured handler failures are configuration errors. The meta gate executes 17 applicable upstream operation pass/fail cases for error responses, ignored and unexpected failures, empty and unsupported operations, dynamic entities, and invalid entity references; focused fakes exercise every remaining expected-error field and typed-result boundary.

The filesystem-facing unified CLI is a Python envelope around the Lua schema/runner layers, like the BSON corpus loader. It discovers every pinned path matching `*/tests/unified/*.json`, the direct Stable API test directory, the read/write-concern operation directory, and the client-bulk causal-consistency fixture; validates exact coverage against `spec/unified/capabilities.json`; applies repeatable glob include filters; and emits versioned reports. Schema validation, per-test inventory, meta-runner execution, and driver execution have distinct report types. Inventory rows use `fixture/path.json::test[N]` identities; execution counters separately name passes, failures, environment skips, unsupported deferrals, scope exclusions, and invalid or incompatible inputs. Zero executed tests always sets `conformant` to false, even when every classification is valid. Runnable identities are grouped by fixture and deployment environment before crossing the Lua process boundary. One bridge invocation loads the fixture and creates one internal-client lifecycle, while `mongodb.unified.lifecycle` still resets initial data and creates and destroys a fresh runner, entity map, clients, sessions, cursors, listeners, threads, and failpoints for every selected test. The bridge returns one machine-readable row for every exact identity; unknown, duplicate, or omitted rows fail the complete batch instead of disappearing into an aggregate count.

Complete execution may be partitioned with an explicit shard count and zero-based index. The first 64 bits of the fixture path's SHA-256 digest select the shard, so all tests inherited from one fixture remain together and the assignment is stable across Python versions and operating systems. Shard reports carry their count and index but deliberately omit global ratchets. Aggregation requires every index exactly once, rejects unknown, duplicate, missing, malformed, wrongly assigned, or classification-changing rows, rebuilds the canonical report in manifest order, and only then enforces the same classified, runnable, and passing ratchets as an unsharded execution.

Execution reports keep performance observations in a top-level `timings` object, separate from test identities, statuses, summaries, and ratchets. A monotonic clock measures preprocessing setup, environment provisioning, each fixture-and-environment batch, and total elapsed execution including cleanup; the report also derives the ten slowest fixture groups. Fixture-group rows are canonicalized by fixture and environment, while the slowest view orders by duration with stable identity tie-breakers. Shard aggregation sums setup, environment, and total worker time, concatenates the disjoint fixture observations, and derives a fresh slowest view instead of trusting shard summaries. These measurements diagnose runner cost but never determine conformance.

The manifest records the pinned specifications commit and assigns each individual `fixture/path.json::test[N]` identity a status, pending owning activity, and concrete reason when it is not runnable. A SHA-256 fingerprint binds the fixture-level setup and test body to the classification. Extracted entities, operations, special runner operations, arguments, event types, matcher operators, outcome use, log expectations, and topology requirements make new upstream capabilities explicit. Missing or stale entries, unknown capabilities or statuses, completed deferral owners, empty reasons, empty discovery, and runnable tests without an executor are hard failures. Classified, runnable, and passing count ratchets cannot move backward. `mongodb.unified.driver` connects the lifecycle's internal client and client, database, and collection entity factories to the public Lua driver. Its initial-data adapter uses majority writes, while its outcome adapter uses primary/local reads sorted by `_id`. Collection operation descriptors translate only declared unified arguments for reads plus `insertOne`, `insertMany`, update, replace, delete, find-and-modify, and collection `bulkWrite`; database aggregation uses the same declared aggregate option translation and cursor collection path, and database view creation maps `viewOn` and `pipeline` through the public administration API. Database entity read preferences retain their maximum-staleness value at this adapter boundary. Find- and generic command-cursor descriptors either return a saved cursor or collect it through the common cursor operations. They translate `timeoutMode` and `cursorType` into the public snake-case option values before validation. The exact empty-batch command-cursor fixture also maps capped-collection setup fields and saves the collection returned by `createCollection`; this support remains test-adapter plumbing over the existing public administration API. Numeric wrappers and return-document enums are converted at this boundary; iterable results are coerced to BSON arrays, and cursors are closed on exhaustion or error before matching. Write request documents become public immutable bulk models, result identifiers are reindexed to unified zero-based keys, and single/bulk results are coerced to their camel-case specification shapes. Structured bulk failures retain partial counts, exact original write-error indices, concern errors, labels, top-level command codes, and server response details for the runner's full expected-error assertions. Each client entity also owns an isolated event collector wired through the public command and pool-monitoring listeners. The SDAM listener is attached for replica-set environments and whenever the fixture observes SDAM; once attached, it retains the latest immutable topology snapshot independently of observed-event filtering, allowing `recordTopologyDescription`, `assertTopologyType`, and bounded `waitForPrimaryChange` operations to inspect actual monitor progress without exposing a test-only public client method. Heartbeat listeners are attached only when requested and normalize started, succeeded, and failed events with the exact awaited boolean for SDAM-category ordering and count assertions. The collector applies observed-event, ignored-command, sensitive-command, and `configureFailPoint` filters at collection time; lifecycle assertions then match exact ordered command sequences or an explicit expected prefix when extra events are allowed. Connection-ready, checked-out, checked-in, connection-closed, pool-ready, pool-cleared, server-description-change, topology-opening, topology-description-change, and topology-closed events are normalized for exact sequence or count assertions, including minimum-pool recovery, phase-sensitive clearing, and shutdown publication. The unified `close` operation closes a client once, while entity cleanup recognizes that closed state and remains deterministic. For fixtures that request `awaitMinPoolSizeMS`, ready-connection events populate the collector's per-data-bearing-pool state, every ready pool must reach `minPoolSize`, and warm-up events are discarded before test execution. Command and reply documents reuse unified matcher semantics, while command/database names, topology-description types, and typed server/service identifier presence are checked directly. Unknown event types and fields, missing events, extra events, and reordered events fail with exact fixture paths. Runtime and URI remain injected.

Unified operation descriptors may provide distinct success and error-result coercers because a method's successful public result and the partial result embedded in its structured error can follow different specification shapes. Collection `insertMany` uses this boundary to expose inserted identifiers on success while matching its unordered-error partial result as a collection bulk-write result with all count fields.

For sharded transaction fixtures, the initial-data adapter pings the same mongos after the final setup write and retains its latest `$clusterTime`; every file-level or dynamically created session advances to that value before transaction operations begin. This implements the unified-runner migration-conflict guard without adding production retry behavior. Targeted failpoint finalizers open their independent cleanup client against the available multiple-mongos URI and still require the exact captured server address, so a connection-closing failpoint can be disabled even when the original transaction selected the second router.

`mongodb.unified.failpoints` implements both `failPoint` and `targetedFailPoint` through one exact selection boundary. ### Connection-string syntax

`mongodb.config.uri` owns parsing for `mongodb://` and `mongodb+srv://` connection strings without importing networking or authentication implementations. It returns an ordered seed list whose entries distinguish hostnames, IPv4 addresses, bracketed IPv6 literals, and encoded Unix socket paths; decoded credentials and authentication database; query pairs in source order; and an SRV marker retained for later resolution. An SRV authority is restricted to exactly one hostname without a port, while one- and two-label hostnames remain valid for the resolver's stricter returned-target checks. Hostnames are normalized to lowercase, ports are range checked, percent escapes and decoded UTF-8 are validated, and repeated query keys produce explicit warnings.

The URI parser intentionally preserves option values as decoded strings. `mongodb.config.options` maps those ordered strings and idiomatic programmatic tables into one immutable value. Programmatic settings take precedence over URI settings, while a private immutable descriptor map routes both paths through the same focused validators for booleans, integers, strings, timeout/pool bounds, read and write concerns, read preference modes/tags/staleness, single-threaded selection compatibility, and TLS policy. Options with exceptional syntax or value rules retain dedicated validators instead of encoding those rules as descriptor flags. Wire-compression configuration retains the declared `snappy`, `zlib`, and `zstd` priority order, defaults the zlib level to `-1`, and accepts only integral levels from `-1` through `9`; it does not load a codec or open a connection. Unknown URI compressor names are omitted with warnings, while programmatic compressor arrays and levels follow the strict programmatic policy. SRV configuration adds a non-negative `srv_max_hosts`, an RFC 6335 service name extended to the DNS label limit, and static `load_balanced` conflict validation. These options are rejected on non-SRV URIs; positive `srvMaxHosts` conflicts with `replicaSet` and `loadBalanced=true`; `directConnection=true` conflicts with every SRV URI; and TLS defaults on only when an SRV parse context has no explicit URI or programmatic TLS value. Stable API is an immutable nested value, requires version `"1"`, and preserves explicitly supplied strict and deprecation flags. A separate syntax-level validation rejects `directConnection=true` with more than one seed before runtime selection.

URI inputs follow the normative warning policy: unknown keys, invalid non-security values, empty typed values, deprecated aliases, and undefined duplicates are ignored or resolved with returned warnings. An explicitly empty `authSource` is the authentication specification's hard-error exception. Repeated read-preference tag sets and equivalent `tls`/`ssl` aliases are the specified no-warning exceptions. Programmatic input is strict, so unsupported keys and invalid values return structured `configuration` errors. Conflicting TLS options remain hard errors even in a URI. The option layer never includes supplied values in its error or warning text, which keeps certificate passwords and other secrets out of diagnostics. `mongodb.discovery.dns` turns an SRV parse result into the initial seedlist before the client constructs any MongoDB transport. It validates every SRV target against the URI hostname's parent domain, preserves the minimum TTL for later polling, samples `srvMaxHosts` with runtime entropy for replica-set and Sharded preprocessing, concatenates the character strings from at most one TXT record, admits only `authSource`, `replicaSet`, and `loadBalanced` TXT defaults, and applies explicit URI and programmatic settings above those defaults. Failed or empty SRV resolution and failed or invalid TXT resolution return structured configuration errors without opening a MongoDB socket. Other additional URI options remain parsed as syntax but are not exposed as accepted programmatic configuration.

Normalized defaults follow the specifications: 100-entry maximum and zero-entry minimum pools, two concurrent connections, 10-second connection and heartbeat intervals, 30-second server selection, 15-millisecond local threshold, primary read preference, retryable reads/writes enabled, and TLS disabled unless explicitly selected or implied by a TLS-specific setting. A legacy URI `wTimeoutMS` creates a default acknowledged write concern even when `w` is absent; CRUD, collection bulk-write, and administration commands translate that public option to the server's `wtimeout` field, while an active CSOT context removes it in favor of the shared `timeoutMS` budget. Downstream pool, SDAM, selection, command, retry, and timeout slices consume this value rather than re-parsing user input.

### OP_MSG framing

`mongodb.wire.op_msg` is the pure-Lua message boundary for opcode 2013. It encodes and decodes the 16-byte little-endian message header, flags, exactly one kind-0 BSON command body, and any number of uniquely named kind-1 document sequences in arbitrary section order. A deterministic request-ID generator assigns positive signed 32-bit IDs and wraps without using platform randomness; response decoding may require an exact `responseTo` match before exposing the body.

`mongodb.wire.op_compressed` is the codec-neutral encoder and decoder for opcode 2012. Encoding accepts an already encoded message body without its 16-byte standard header, passes those exact bytes and any compressor-specific level to an injected runtime provider, and emits a new request header followed by the original opcode, uncompressed body size, compressor ID, and compressed bytes. Decoding validates both envelope and declared uncompressed sizes before selecting a provider from the complete runtime registry by compressor ID; it does not assume the compressor selected for outgoing messages. The recovered standard header retains the envelope request and response identifiers and original opcode, after which the command executor uses the existing OP_MSG decoder. Unknown IDs, malformed frames, size mismatches, and provider failures become structured protocol errors. Neither this module nor any other core wire module imports a native compression library.

The codec rejects checksum-bearing messages because CRC-32C support is intentionally absent, rejects unknown required flag bits and response-only misuse, and ignores unknown optional high bits as the specification requires. Declared frame/section/BSON lengths are checked before slicing or decoding, and negotiated `maxMessageSizeBytes` and `maxBsonObjectSize` limits are enforced on both paths. The size-accounting API uses the same encoding preparation as the wire writer, so later bulk batching can make decisions without maintaining a second overhead formula.

### Hello and single-connection commands

`mongodb.handshake.metadata` builds one immutable baseline client document when a public client is constructed. The driver name and version are fixed by the package, the normalized application name is optional and limited to 128 bytes, and the required OS type falls back to `unknown`; non-empty OS name, architecture, version, and platform facts are copied from the optional runtime metadata boundary. That boundary also supplies snapshots of relevant environment variables and root-filesystem presence. AWS Lambda, Azure Functions, Google Cloud Functions, and Vercel signals select the normative fixed `env.name`; Vercel takes precedence only over AWS, while every other ambiguous provider combination omits FaaS fields. Optional region and int32 memory/timeout facts are copied only when valid. Docker and Kubernetes facts form an independent container document and can coexist with FaaS metadata. The default Copas adapter discovers these facts once, while injected runtime facts make tests and embedded runtimes deterministic. The builder measures the complete encoded BSON document and, only while it exceeds 512 bytes, cumulatively reduces environment metadata to `env.name`, reduces OS metadata to `os.type`, removes `env`, and then truncates or removes `platform` without splitting UTF-8. If wrapper suffixes still exceed the limit, their version and name suffixes are truncated while the fixed Lua driver identity remains intact. Application and OS type also remain unchanged. The client snapshots runtime facts and the initial wrapper tuple before opening a socket. Each later `append_metadata` call validates one case-sensitive name/version/platform tuple, treats empty optional strings as unset, rejects the `|` delimiter, and ignores exact duplicates. A unique tuple atomically replaces the current bounded metadata snapshot used by future monitor, RTT, pooled application, reconnect, and discovered-member connections; established sockets retain their original immutable document, and an update alone creates or closes no connection.

`mongodb.command.executor` owns the protocol lifecycle on one exact-I/O transport connection. Its first handshake uses OP_MSG legacy `ismaster` with `helloOk: true`, unless Stable API or load-balanced mode requires modern `hello`; every hello carries the string-valued backpressure version, while only the initial hello carries the immutable client metadata and an ordered array of configured compressors that are available from the injected runtime. A load-balanced application executor also adds `loadBalanced: true` only to that initial hello. It accepts the connection only when the successful response contains a BSON ObjectId `serviceId`; absence returns the normative client error and closes the physical connection, while an invalid type is a protocol error. The executor retains a valid service identifier in connection state for later service-specific pool behavior. The executor selects the first advertised compressor name in client priority order that appears in that socket's response, retains the provider only in that executor's connection state, and treats no overlap as a valid uncompressed connection. Monitoring, RTT, pooled application, standalone, and reconnect executors therefore negotiate independently; later hello requests neither resend the compression offer nor mutate the established selection. A successful legacy negotiation permanently switches later hello requests to the modern command without resending handshake arguments. Awaitable monitoring hello requests set `exhaustAllowed`; the executor consumes each chained `moreToCome` response using the preceding server message identifier and sends a new request only after the stream ends. Other commands still reject unexpected streaming replies. The executor records the reply's BSON/message/batch limits and uses the negotiated per-connection values for later encoding and framed reads.

Commands are copied from the caller's ordered BSON document, preserving the command name as the first field. Stable API fields and the `$db` global argument are appended to the copy, so caller state is never mutated. Before wire framing, the case-insensitive compression policy withholds the negotiated provider from `hello`, legacy `ismaster`, `saslStart`, `saslContinue`, `getnonce`, `authenticate`, `createUser`, `updateUser`, `copydbSaslStart`, `copydbgetnonce`, and `copydb`; every other command remains eligible. For an eligible command on a negotiated connection, the executor encodes the ordinary OP_MSG body and then replaces its standard header with OP_COMPRESSED using the same request identifier, flags, sequences, deadlines, and connection-local provider; zlib receives the configured level. Monitoring starts from the logical BSON envelope and retains that request identifier, so retries and events are independent of wire framing. Replies may use either OP_COMPRESSED or ordinary OP_MSG regardless of request framing. The policy shares the normative always-sensitive command set with monitoring security but does not alter the logical command document observed by monitoring. Request IDs are correlated before a reply is exposed; I/O failures, malformed frames, invalid `ok` fields, and unexpected streaming replies close the connection. An `ok: 0` reply remains a server operation failure without closing the connection and retains its numeric code, code name, labels, timeout/retryability classification, server address, and immutable BSON response details.

`mongodb.command.hello` is the immutable per-connection capability model. It validates and supplies defaults for negotiated wire, BSON, message, batch, and logical-session fields, validates and exposes an optional load-balancer service identifier, and exposes the server's basic readability/writability shape for later SDAM work. It does not select servers, pool connections, authenticate, or import runtime-specific networking; those responsibilities remain in their dedicated layers.

### Authentication

`mongodb.config.credentials` converts the parsed URI and normalized options into one immutable credential before the client opens a MongoDB socket. A username/password delimiter selects authentication; a database path or `authSource` alone does not. Default, SCRAM-SHA-1, SCRAM-SHA-256, and PLAIN credentials require both a non-empty username and a supplied password and reject mechanism properties. SCRAM chooses an explicit `authSource`, then the URI database, then `admin`; PLAIN chooses an explicit source, then the URI database, then `$external`. MONGODB-X509 accepts an optional certificate subject as its username, rejects passwords and mechanism properties, and always uses `$external` regardless of the URI database. MONGODB-AWS creates a `$external` credential shell only when the URI supplies no access key, secret key, or session token; ordered provider slices resolve its actual credentials at authentication time. This follows DRIVERS-3131, so the two retained legacy fixtures that still expect explicit AWS URI credentials are executed and recorded as superseded exclusions instead of being made to pass through hostname-dependent behavior. Invalid combinations return value-style configuration errors containing only field names and fixed mechanism text. The same credential identity is reused by every application connection so mechanism caches remain effective, while monitor and RTT connections continue without credentials.

MONGODB-OIDC built-in environments also normalize to an immutable `$external` credential shell without a password. `ENVIRONMENT` must select `test`, `azure`, `gcp`, or `k8s`; the test environment rejects a username, Azure and GCP require a non-empty `TOKEN_RESOURCE`, and test and Kubernetes reject that property. Programmatic configuration may select a function-valued `OIDC_CALLBACK` machine identity or `OIDC_HUMAN_CALLBACK` human identity instead, but an environment and the two callback kinds are mutually exclusive. `TOKEN_RESOURCE` remains limited to Azure and GCP. A human callback receives either a copied custom `ALLOWED_HOSTS` dense string list or the immutable normative MongoDB service-domain and loopback defaults; machine callbacks and built-in environments reject that property.

`mongodb.auth.oidc` owns this mechanism-specific normalization, while the general option layer admits callback functions and allowed-host tables only from programmatic input. The normalized credential receives copied immutable mechanism properties rather than retaining mutable caller or parser state. URI configuration continues to accept only the environment and token-resource strings: callback and allowed-host material is rejected without rendering its value, colons remain valid inside a token resource, and comma-bearing resources use the programmatic mechanism-property table because comma separates URI properties. Callback functions and token-resource contents likewise never enter structured configuration diagnostics.

Before human callback authentication, the connection boundary passes the already-selected normalized server host—not a new address or networking capability—into the OIDC policy check. An allowed entry matches either the exact host or, when it begins with `*.`, a subdomain ending at that complete dotted suffix; a wildcard does not match the suffix root, a partial label, or a longer attacker-controlled suffix. A missing or unlisted host returns a fixed credential-free authentication error before invoking the callback or sending a SASL command. Machine callbacks do not apply this host policy.

Uncached human authentication sends an optional principal name in the first `$external` `saslStart`, requires an incomplete response with one integer conversation identifier and a generic-binary BSON `IdpInfo`, and validates the required issuer plus optional client identifier and string scope list before invoking user code. The callback receives that information as nested immutable, snake-case Lua values in a version-one context with a five-minute deadline independent of CSOT; cancellation remains available through the runtime boundary. A valid callback access token completes the same conversation through `saslContinue`. Callback, IdP, command, encoding, and continuation failures return fixed token-free authentication diagnostics.

The opaque human access-token generation is retained in the shared per-client and per-connection cache so later connections use one-step SASL without another callback. Authentication error 18 invalidates only the matching generation, including when an older connection fails after a newer token exists; other failures retain it. A successful human callback also retains the validated IdP information and its optional refresh token. Human authentication tries at most one cached access token, one access token obtained from the cached refresh credential, and one new two-step conversation, in that order. Rejection of the cached access token resumes at the refresh tier when available; rejection of the refreshed access token clears the refresh credential before the new two-step callback, which therefore receives only the new IdP information. The new two-step result is never retried in the same authentication attempt, while non-authentication failures return without evicting cache fields. Human callbacks share per-client serialization, cache rechecking, and the 100-millisecond start interval while releasing coordination before any SASL command. Expiry remains advisory and unretained.

Machine authentication invokes the configured callback with an immutable version-one context containing the normalized username, cancellation token, absolute deadline, and remaining timeout. Its callback window is capped at 60 seconds and shortened by an earlier caller deadline. A non-empty access token is encoded as the one-step `JwtStepRequest` payload for a single `$external` `saslStart`; callback failures, malformed callback results, command failures, and malformed SASL replies become credential-free structured authentication errors. The exact pinned OIDC read and write cases run through a deterministic loopback server without exposing the token.

Before an authenticated application connection sends `hello`, OIDC may attach a one-step `JwtStepRequest` only when that credential already owns a cached access-token generation. The same generation is recorded in the connection cache. A complete successful `speculativeAuthenticate` response finishes authentication without another SASL command; a missing, incomplete, or malformed response clears only that connection entry and runs the ordinary cached-token flow, leaving the client generation available. An uncached credential never calls its provider merely to speculate. The hello command and response remain sensitive at the command-security boundary.

An authenticated OIDC application connection handles server code 391 before it is returned to its pool. It invalidates that connection's exact cached-token generation, runs the standard OIDC SASL flow directly on the same connection under the operation's cancellation and deadline, and re-attempts the original command exactly once regardless of ordinary read/write retry eligibility. Reauthentication never sends `hello` or speculative authentication. A reauthentication failure or any error from the single re-attempt is returned without another reauthentication attempt.

`mongodb.auth.oidc_providers` adapts a configured built-in environment to the same internal machine-callback boundary without granting authentication code direct process, filesystem, socket, TLS, or cryptography access. The test integration reads `OIDC_TOKEN_FILE` through `runtime.environment`, reads at most one MiB through `runtime.file` under the callback deadline and cancellation token, and strips surrounding whitespace. The Kubernetes integration first selects a present `AZURE_FEDERATED_TOKEN_FILE`, then a present `AWS_WEB_IDENTITY_TOKEN_FILE`, and otherwise the conventional service-account token path; an explicitly empty higher-precedence path fails instead of falling through, and token bytes including a trailing newline remain opaque. Both file providers reject absent, unreadable, empty, or oversized content with a fixed provider-classified authentication error.

The Azure integration percent-encodes the configured token resource and optional username into the fixed IMDS identity endpoint, sends the required metadata and JSON headers through `runtime.http`, and propagates the callback deadline and cancellation token into that adapter. It accepts only status 200 with a bounded JSON document containing a non-empty access token and positive decimal-string `expires_in`. The GCP integration percent-encodes the token resource as the audience of its fixed metadata identity endpoint, sends the required `Metadata-Flavor` header through the same HTTP adapter, and accepts only a status-200 non-empty response body while preserving its opaque bytes. For both metadata providers, a non-200 response body remains available as structured provider detail as required by the authentication specification, while malformed, transport, timeout, and cancellation failures use fixed diagnostics. Provider results enter the existing coordinated cache and one-step SASL flow, and their callbacks do not add another cache.

The immutable credential identity owns one client access-token cache, while each command executor records the exact opaque token generation used on that connection. A cached token avoids another callback across connections. Server authentication code 18 invalidates the client token only when that connection still refers to the current generation; a stale connection therefore cannot discard a newer token even when their strings are equal. A cached-token rejection fetches or observes one replacement and retries authentication once, while a newly fetched rejection is returned without another callback. Other failures retain the cache. The optional callback expiry duration remains validated but, as required by the current specification, is advisory and does not evict a cached token.

One runtime lock per client serializes machine callback execution. A waiter rechecks the access-token cache after acquiring that lock, so it reuses a token produced by an earlier callback instead of invoking the provider again. Callback start times are separated by at least 100 milliseconds using only the runtime monotonic clock and cancellable sleep; lock acquisition and rate-limit waiting honor the caller's absolute deadline and cancellation token. The lock is released after the callback result is cached and before any SASL command, preserving `maxConnecting` concurrency and preventing server I/O from blocking other callback waiters.

`mongodb.auth` dispatches the immutable credential after hello. An explicit mechanism bypasses default SCRAM negotiation. `mongodb.auth.plain` sends one RFC 4616 initial response containing an empty authorization identity, username, and password to the selected source with `autoAuthorize: 1`; it requires the server to complete that SASL exchange in its first response. `mongodb.auth.x509` sends one `authenticate` command to `$external`; it includes `user` only when the application supplied a certificate subject. Command failures and malformed replies become credential-free structured authentication errors. Neither mechanism performs runtime-specific work: deployments are expected to protect PLAIN with TLS, while X.509 client certificate and private-key loading stays within the TLS runtime adapter.

`mongodb.auth.aws` accepts only an internally resolved access key, secret key, and optional session token, then runs the two-command MONGODB-AWS SASL exchange on `$external`. Its first message uses exactly 32 bytes from runtime entropy and advertises no channel binding. The server challenge must contain a 64-byte nonce beginning with those client bytes and an STS host with the normative length and label shape. The module derives the STS region, formats the runtime wall clock as UTC without consulting process time, and builds the required SigV4 canonical request using only runtime SHA-256 and HMAC-SHA-256. The secret key participates only in adapter-backed HMAC derivation; it is absent from SASL payloads and structured errors. A temporary session token is both signed and returned in the required second payload, whose command-monitoring representation remains covered by the shared SASL redaction policy.

`mongodb.auth.aws_credentials` begins the provider chain by dynamically reading `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and optional `AWS_SESSION_TOKEN` through `runtime.environment` immediately before each uncached authentication. The Copas adapter delegates that capability to the process environment, while the fake owns a mutable isolated map; core authentication never calls `os.getenv`. A complete pair becomes a new immutable internal credential and is not cached, so a later authorization observes refreshed Lambda-style values. An absent environment permits the next provider, while any partial or empty combination fails as a credential-free structured authentication error.

The provider chain holds at most one non-environment credential and the provider that produced it. A cached value remains authoritative over later environment changes only while its expiration is more than five minutes away; at that boundary the same provider is called to refresh it before any environment fallback. Environment credentials never enter this cache. Provider output must contain a complete access/secret pair, optional non-empty session token, and a future Unix expiration, and provider failures are converted to credential-free authentication errors. Any authentication failure invalidates the cache only when the failed credential is the exact cached value, allowing the next authorization to fetch a replacement without affecting environment or unrelated authentication state.

When both `AWS_WEB_IDENTITY_TOKEN_FILE` and `AWS_ROLE_ARN` are present, `mongodb.auth.aws_web_identity` is the next provider after environment access-key credentials. It reads the token only through `runtime.file`, uses the configured session name or derives one from runtime entropy, and sends the manually encoded `AssumeRoleWithWebIdentity` request through `runtime.http` with a JSON response preference. The response must contain a complete temporary credential and a future UTC expiration before it enters the shared five-minute AWS cache. File, HTTP, timeout, cancellation, JSON, status, and expiration failures become credential-free authentication errors; paths, token contents, STS bodies, and credentials do not enter diagnostics.

When web identity is not configured and `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` is present, `mongodb.auth.aws_ecs` appends that absolute-path value only to the fixed `http://169.254.170.2` ECS link-local origin. It rejects empty, non-path, fragmented, whitespace-bearing, or control-bearing values before networking. The provider performs one adapter-backed GET with the earlier of the client deadline and a ten-second provider deadline, carries cancellation unchanged, and accepts only a successful bounded JSON response containing a complete access key, secret key, `Token`, and future UTC expiration. Valid credentials enter the same five-minute provider cache; endpoint, response, timeout, cancellation, and validation failures remain credential-free authentication errors.

The same provider accepts `AWS_CONTAINER_CREDENTIALS_FULL_URI` only when the relative URI is absent. A syntactically valid HTTPS origin may use any DNS name or IP address; plain HTTP is restricted to IPv4 and IPv6 loopback addresses plus the documented ECS and EKS link-local metadata addresses. URI credentials, fragments, invalid ports, malformed DNS/IP hosts, and non-local HTTP origins fail before the runtime HTTP adapter is called. This keeps the full-URI extension's SSRF boundary separate from response parsing and preserves the AWS relative-URI precedence rule.

Full-URI requests may carry one container `Authorization` header. `AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE` takes precedence and is read as-is through `runtime.file` with the same deadline and cancellation token as the request plus a 64 KiB limit; `AWS_CONTAINER_AUTHORIZATION_TOKEN` is consulted only when no file is configured. Empty, oversized, unreadable, or control-bearing values fail before HTTP without falling back between configured sources. Relative ECS requests ignore both authorization inputs. Provider errors retain timeout or cancellation classification while omitting token values and file paths.

When no earlier provider is configured, `mongodb.auth.aws_ec2` completes the fallback chain through the fixed EC2 Instance Metadata Service origin. It starts an IMDSv2 session with a token `PUT`, discovers the validated IAM role name with a token-authenticated `GET`, and fetches that role's temporary credential with a second token-authenticated `GET`. All three operations share the earlier of the caller deadline and one ten-second provider deadline and carry the same cancellation token. Token, role, status, size, JSON, success-code, credential, and future-expiration validation occurs before the result enters the shared five-minute cache. The provider retains only fixed endpoint paths and returns credential-free structured failures, so IMDS tokens, role names, response bodies, and credentials cannot enter diagnostics.

The default Copas runtime supplies bounded binary file reads and a small bounded HTTP/1.1 client for credential providers. HTTP resolves and connects through the existing socket adapter, wraps HTTPS through the TLS adapter with the request host as the server name, and carries the caller's absolute deadline and cancellation token through connect, write, and read. It accepts content-length, chunked, or connection-close response framing, rejects ambiguous or malformed framing, and caps response headers and bodies. Authentication and provider modules see only the runtime `file` and `http` interfaces; they never import process files, sockets, or TLS implementations.

`mongodb.auth.scram` runs SCRAM-SHA-256 and SCRAM-SHA-1 over a handshaken command executor. It generates each client nonce from 32 runtime entropy bytes, escapes the raw username for the SASL name, enforces the 4,096-iteration minimum, validates that the server nonce begins with the client nonce, and compares the expected server signature in constant time. It sends `skipEmptyExchange`, supports the older third empty exchange, and caches derived client/server keys per credential identity with mechanism, salt, and iteration guards.

SCRAM-SHA-256 prepares only the password with `mongodb.auth.saslprep`; usernames remain raw as MongoDB requires. The pure-Lua implementation maps, normalizes, prohibits, and performs bidirectional checks against checked-in Unicode 3.2 tables generated by `tools/generate_stringprep_tables.py`. The generator renders the complete artifact deterministically in memory; `--check` compares bytes and reports drift without touching the worktree, and `make test-generated` enforces that invariant in the fast gate. SCRAM-SHA-1 preserves MongoDB's legacy behavior: neither field is prepared, and the password first becomes the lowercase MD5 hex digest of `username:mongo:password` before PBKDF2-SHA-1.

SASL commands pass through the executor so normal deadlines, cancellation, and command monitoring apply. Monitoring redacts their command/reply bodies. Authentication converts server command failures, malformed payloads, nonce/signature failures, and SASLprep rejection to credential-free structured authentication errors; it never retains response payloads, passwords, salts, proofs, or signatures in those errors.

### Command monitoring

`mongodb.monitoring` publishes immutable command-started, command-succeeded, and command-failed events synchronously around application command I/O. The executor supplies a single request ID to each correlated pair, accepts an optional operation ID for multi-command work, reports the database and connection identities, and reconstructs OP_MSG document sequences as arrays in the started event. After a load-balanced handshake, every outcome in the correlated command pair carries that physical connection's validated `serviceId`; ordinary connections retain a nil service identifier. Durations come from an injected monotonic clock capability and cover the command exchange. Initial connection handshakes are excluded from command monitoring.

Listeners are copied at monitor construction and invoked in registration order. Each callback runs behind an isolated protected call, so listener failures cannot change command results or prevent later listeners from observing the event; an optional error callback receives listener failures under the same isolation rule. Event and BSON values are immutable, preventing one listener from changing what another listener observes.

Authentication commands (`authenticate`, SASL commands, nonce/user/copydb commands) and hello commands containing `speculativeAuthenticate` publish empty command and reply documents. A shared command-security policy also replaces the public error message for a sensitive server failure and restricts its response details to `code`, `codeName`, and `errorLabels`; monitoring applies the same projection before listener dispatch. Network and other client-side failures remain inspectable because they do not contain server authentication payloads. This keeps listener and public diagnostic paths aligned without exposing credential-bearing values.

### Core API and monitored topology lifecycle

`mongodb.client` is the public constructor boundary. It separates runtime and listener capabilities from programmatic driver options, parses the URI, normalizes the initial configuration, and resolves `mongodb+srv` SRV and TXT inputs before validating the merged result, constructing credentials, or opening a MongoDB socket. Resolved SRV seedlists enter the monitored topology path; ordinary URIs without `replicaSet` retain the direct single-seed lifecycle unless a positive `minPoolSize` or an SDAM listener requires a monitored topology and its connection pool. An implicitly monitored standalone begins as Unknown and becomes Single after its first successful hello; direct connection mode begins as Single. If the direct bootstrap hello identifies a mongos, the client closes that temporary executor and rebuilds the seed through the monitored topology path; the Unknown topology becomes Sharded, read and write selection admit Mongos servers without replica-set primary semantics, and ordinary plus cursor commands use the selected pool. The topology captures its hello as immutable capability input, so a concurrent background application-connection failure cannot turn client construction into an eager checkout failure. A replica-set URI accepts multiple seeds, creates a monitored topology, and discovers the authoritative host list from hello responses. Each application connection is upgraded with normalized TLS policy, sent the client's metadata-bearing initial handshake, and authenticated before entering its server pool. Monitor connections use the same runtime/TLS transport and metadata snapshot but do not authenticate or negotiate mechanisms. An application hello requests `saslSupportedMechs` only for a default-mechanism credential; the lifecycle selects SCRAM-SHA-256 when advertised and otherwise uses the required SCRAM-SHA-1 fallback. Explicit SCRAM mechanisms bypass negotiation. Multiple ordinary seeds without `replicaSet`, Unix sockets, remaining sharded behavior, and load balancing remain explicit errors or later v0.4 classifications.

An SRV-created topology carries only the original hostname, service name, `srvMaxHosts` bound, and latest minimum TTL into `mongodb.topology`; DNS transport remains in the runtime adapter and SRV validation/randomization remains in `mongodb.discovery.dns`. One cancellable topology task polls only while SDAM type is Unknown or Sharded. A successful scan retains unchanged server descriptions, monitors, and pools; removes disappeared addresses; and creates newly selected addresses as Unknown. A positive `srvMaxHosts` retains surviving members before randomly filling remaining capacity. Invalid returned domains are ignored, while DNS failures and empty or wholly invalid results leave the topology unchanged and temporarily use `heartbeatFrequencyMS`. Successful scans schedule from completion using the lowest valid TTL with a 60-second floor. Transition to Single, either replica-set type, or LoadBalanced cancels polling, and client close wakes and joins the polling task before closing remaining server resources.

`mongodb.api` owns immutable client, database, and collection handles whose state is kept outside the visible tables. Database names reject the server-prohibited characters except for the authentication namespace `$external`; collection names reject empty components, null bytes, invalid dots, and unsupported dollar forms. Database and collection handles inherit normalized read concern, read preference, and write concern, with validated per-handle overrides. A database runs a command through the shared executor without changing the caller's ordered BSON document. Its `aggregate` method uses aggregate target `1`, parses the collection component from the server-returned namespace, registers the cursor with the owning client, and otherwise shares collection aggregation's command and cursor boundaries. Client close is idempotent and closes the executor once; all derived database handles observe the same closed state and return a structured `client` error before I/O.

`mongodb.topology_executor` gives the existing API handles the same executor contract for replica sets and sharded deployments. It classifies read and write commands, applies a per-operation inherited read preference when selecting a server, and adds the normative camel-cased `$readPreference` OP_MSG argument with optional tags and maximum staleness. Normalized Lua tag maps become ordered BSON documents with stable key ordering at this wire boundary. It waits for the monitored description to yield a selectable server, checks a connection out of that server's pool, and always checks it back in. An optional selection callback receives the immutable selected address and server type; callers may also require one exact address without reaching into topology state. Network, protocol, timeout, and server failures feed their address and connection generation back into SDAM before the next selection. Standalone, replica-set, and sharded API objects depend only on configuration, runtime, transport, command, authentication, monitoring, topology, selection, and pool interfaces; runtime-specific networking, TLS, and cryptography remain behind adapters.

### GridFS bucket handles

`database:gridfs_bucket` and the top-level `mongodb.gridfs_bucket` factory construct the same immutable bucket handle without opening a connection or issuing a command. A bucket owns configured `<bucket>.files` and `<bucket>.chunks` collection handles, defaults to `fs` and 255 KiB chunks, and inherits the database's read concern, read preference, write concern, and operation timeout unless overridden. Construction rejects unacknowledged writes and invalid chunk sizes before I/O; `disable_md5` is accepted as a compatibility no-op because this driver never computes GridFS MD5 values. The unified bucket entity translates the exact camel-cased configuration into this public boundary. Unknown unified bucket operations continue to fail instead of being skipped.

An upload stream is also an immutable handle with externally observable mutable state: it exposes its generated ObjectId or caller-supplied id immediately, and `closed` changes only after the files document is acknowledged. Closing an empty stream creates no chunk and inserts one files document with Int64 zero length, the selected chunk size, filename, and a close-time BSON datetime obtained from the runtime wall clock. The first upload write on each bucket checks whether the files collection is empty using primary read preference; only an empty collection triggers discovery of the required files and unique chunks indexes. Ordered key comparison treats Lua, BSON int32, BSON int64, and BSON double directions with the same numeric value as equivalent, and missing indexes are created without the background option. The successful precondition is cached on the bucket, while index or files-insert errors remain structured values and leave the upload open for the caller to retry.

Upload `write` calls accept byte strings and retain at most the current partial chunk between calls. Each full chunk is inserted immediately with the file id, a monotonically increasing zero-based `n`, and generic BSON binary data; close inserts the remaining non-empty partial chunk before the files document. A per-file chunk-size override controls both boundaries and the stored `chunkSize`. The files document records the exact Int64 length and optional immutable BSON metadata, never includes `md5`, and no upload issues `filemd5`. Once a chunk write fails, the stream retains and returns that original structured error from later writes or close without deleting already-inserted orphan chunks or committing a files document. Writes after a successful close fail locally without I/O.

Explicit abort marks the upload closed and aborted and discards its buffered partial chunk before cleanup starts. It deletes all chunks for the upload id and then defensively deletes the corresponding files document, using the bucket collections and their inherited write concern. A cleanup error is retained and returned unchanged by a repeated abort, while write and close reject the terminal aborted state without I/O. This cleanup is exclusive to explicit abort; ordinary index, chunk, or files writes still preserve the original failure and any orphan chunks.

Upload convenience methods accept either a byte string or a value with a `read` method, consume the source in chunk-sized reads, and never close the caller's source. The generated-id form returns its ObjectId; the custom-id form reports completion without returning the already-known id. A returned or raised source-read error aborts the upload and preserves the original error even if cleanup also fails, while a server operation failure retains the ordinary orphan-chunk behavior. The complete upload, including first-write index discovery and both collection inserts, runs inside one operation-timeout context. Unified `upload` and `uploadWithId` validate `$$hexBytes`, construct a readable source, and map camel-cased upload options into this same public boundary. All nine pinned upload fixtures and all nine directly coupled CSOT upload fixtures execute without MD5 behavior.

A download stream retrieves and validates the files document before returning, accepts all exact integral BSON numeric representations for `length` and `chunkSize`, and retains that operation's absolute timeout deadline for later reads and cursor cleanup. Zero-length files return an empty stream without querying chunks. Non-empty reads query chunks by file id in ascending `n` order, validate every consumed chunk number and byte length, and return missing files and corrupt required chunks as distinct structured client errors. Bounded reads stop validation at the requested byte position. Lua-style `seek` supports `set`, `cur`, and `end`, closes the previous cursor, and starts the next query at the calculated chunk instead of rereading earlier chunks; `tell` reports the byte position and close is idempotent. `download_to_stream` copies through this validated path in bounded 64 KiB writes under one inherited absolute timeout. It always closes its internal download stream, never closes the caller-owned destination, and returns the first structured read, destination-write, or cursor-close failure. Filename downloads select a files document by `uploadDate`: non-negative revisions sort oldest-first and skip the revision, while negative revisions sort newest-first and skip `-revision - 1`; a second existence query distinguishes a missing filename from an out-of-range revision. ### Sessions and causal consistency

`mongodb.session` owns client sessions and the server-session pool. Logical session IDs are UUID-subtype BSON documents generated from the runtime entropy adapter. Explicit sessions default to causal consistency; implicit sessions disable it. Snapshot sessions normalize that default to false, reject explicit causal consistency, and may retain an initial BSON snapshot timestamp only when snapshot mode is enabled. These option conflicts and type failures are programmer errors resolved before allocating a server session. The client passes its immutable handshake wire version into session decoration; a snapshot session on a server below wire version 13 returns the normative client error before the downstream executor can emit an application command. At supported wire versions, decoration creates or replaces the command read concern with `level: "snapshot"` for reads, writes, metadata commands, and generic commands, ensuring unsupported operations reach the server and receive its normative error. A snapshot session without an initial time captures the first valid cursor-level or top-level `atClusterTime` reply and never replaces it; every later command adds that timestamp to its snapshot concern. An explicitly initialized time takes the same decoration path from the first command. The read-only `get_snapshot_time` accessor returns that BSON timestamp, or the documented unset `nil` value for a non-snapshot session; immutable session handles prevent callers from overwriting it. Ordinary sessions do not take the snapshot decoration branches. A `LoadBalanced` topology reports session support even though its synthetic server omits `logicalSessionTimeoutMinutes`; the client creates explicit and implicit sessions in that mode, and its server-session pool ignores any reported timeout instead of pruning idle entries. Server-session creation, release, and ordinary-topology stale checks use only the injected runtime's monotonic clock, so elapsed-idle bookkeeping never reads process wall time. Clean, unexpired server sessions return to a LIFO pool, while dirty and expired sessions are discarded. Ending a session is idempotent, ended sessions cannot decorate commands, and a manager rejects sessions belonging to another client. Command decoration assembles its ordered copy through local session-validation, transaction, cluster-time, and read-concern helpers; these helpers do not expand the module surface or own execution. Client shutdown ends active sessions, drains the pool into one `endSessions` command, ignores that cleanup command's operational result, and then closes the underlying executor.

Snapshot sessions reject transaction start at the session state boundary before allocating transaction state or reaching command execution. The unified session adapter exposes `getSnapshotTime` as a zero-argument BSON result and resolves a string `sessionOptions.snapshotTime` through the typed entity map before starting a new session. Unknown operation arguments and missing or mistyped timestamp entities fail as configuration errors before driver I/O. The three pre-5.0 guard identities are runnable, but modern local and fast-CI deployments report their upstream maximum-server-version requirement as an environment skip; the deterministic executor test is the local proof of the client-only boundary until an applicable compatibility profile executes them. All twelve snapshot-concern server-error identities and all thirteen direct snapshot-session identities execute against the applicable standalone or replica-set environment and pass without runner-side command emulation.

`mongodb.session_executor` decorates the existing standalone or topology executor without importing a runtime. It copies ordered commands, attaches `lsid`, gossips the greatest client/session `$clusterTime`, preserves configured read concern, merges causal `afterClusterTime` when applicable, and advances cluster and operation times from replies. Network and protocol failures dirty the associated server session, including intermediate retry attempts. A normal command owns one implicit session; multi-batch bulk work uses one operation context, while cursors retain their context across `getMore` and `killCursors` and release it on exhaustion, explicit close, malformed replies, or command failure. Explicit sessions flow through the same CRUD, bulk, administration, command, cursor, and unified-driver option boundary.

### Explicit transactions

In load-balanced mode, a cursor created inside a transaction borrows the session-owned physical connection rather than taking a second checkout. Its `getMore` and `killCursors` commands continue through the session pin, cursor closure does not return that shared connection, and the transaction's terminal unpin boundary remains its sole release owner. Ending a session also clears any connection retained after commit, returning a reusable socket or completing check-in for an already failed socket exactly once.

`mongodb.session` owns the explicit transaction state machine and transaction-number allocation. `start_transaction` merges client concerns, session defaults, and call overrides, rejects an active transaction or unacknowledged write concern, and increments the server session's transaction number exactly once. Decoration adds `startTransaction` and the transaction read concern only to the first command, attaches `autocommit: false` and the stable transaction number to every command, strips operation and handle write concerns, and preserves causal `afterClusterTime`. Size measurement includes the same wire fields without consuming the starting state. Read commands validate operation-level and transaction-level preferences independently, so a primary preference from one source cannot mask a non-primary preference from the other; violations return structured client errors before executor I/O.

Commit and abort commands reuse the decorated executor path. Empty transactions complete locally; invalid state transitions do not perform I/O; ending a session aborts an active transaction. Retryable commit and abort failures make one new attempt. Both commands also retry a sanitized authentication failure that preserves a retryable handshake-network marker, even when `retryWrites=false`; the fresh connection reuses the transaction's `lsid` and `txnNumber`, and abort enters `aborted` exactly once after cleanup succeeds. Retried and repeated commits promote `w` to `majority`, preserve journal and explicit timeout settings, and otherwise use a 10-second write-concern timeout before entering `committed`. Non-control network failures inside a transaction gain `TransientTransactionError` and cannot trigger ordinary read/write retries; uncertain commit failures gain the required `RetryableWriteError` and `UnknownTransactionCommitResult` labels. In load-balanced mode, the first active transaction command transfers its physical connection checkout to the session; every later operation and repeated commit uses that same connection, which remains pinned after successful commit until a later normative unpin boundary. Ordinary CRUD and commit errors retain that healthy pin, while an ordinary abort error terminates ownership and returns it. A transient application error clears the session pin before returning; if the error came from the network, pool failure handling discards the failed physical connection instead of checking it back in. A transient commit error also releases both server and connection pins; a retryable commit does so before its single retry, allowing that retry to pin a fresh connection while preserving its transaction number, recovery token, write concern, and labels. On a sharded deployment, the first active transaction command records a pin only when topology selected a Mongos server. Every later application or transaction-control command supplies that exact address through the executor contract, including repeated commits and session-targeted failpoint setup. A command error without `TransientTransactionError` retains that pin for subsequent transaction work; the automatic upstream matrix proves this across 20 insert, update, delete, find-and-modify, collection and client bulk-write, find, aggregate, distinct, and generic-command paths. After application-error label normalization, `TransientTransactionError` clears the pin before the error returns; this covers server-provided shutdown labels and driver-synthesized network or timeout labels across the same operation families. Each successful active-transaction response that contains a recovery token replaces the session's internal token reference, and transaction-control decoration appends that exact BSON document unchanged to commit and abort. The committed state retains the token for explicit commit retries; starting a new transaction or transitioning to no transaction replaces the transaction state and clears it without exposing mutable token state. Abort unpins after success, failure, or a locally empty transaction and before retry selection. Transient or unknown commit outcomes, a new transaction, and a non-transaction session operation also clear the pin before their next selection boundary. Starting that new transaction releases the retained physical connection before replacing transaction state, preserving the logical session id while advancing the transaction number. A non-transaction session operation releases the connection before command decoration resets committed transaction state, reuses the logical session id without transaction fields, and does not retain its ordinary checkout. Thirty-nine automatic transient-error identities and two recovery-token-coupled identities prove the application-error boundary against two real mongoses.

`with_transaction` layers the convenient API over that explicit state machine. It invokes the callback with the session, returns the callback's first result after a successful commit, and aborts an active transaction when the callback returns or throws a structured error. `TransientTransactionError` restarts the whole transaction; `UnknownTransactionCommitResult`, except code 50, retries only commit. Without CSOT both loops share a fixed 120-second budget and whole-transaction retries sleep with bounded exponential jitter sourced from the runtime entropy adapter. With CSOT the inherited session or operation deadline replaces that budget and jitter, and abort cleanup refreshes the original timeout so cleanup receives one real command attempt. A callback that explicitly commits or aborts returns without an extra commit. The callback may run more than once, so external side effects must be idempotent.

### Client-side operation timeout

`mongodb.operation_timeout` owns coroutine-local operation context above the executor stack. Public client, database, collection, cursor, session, and GridFS convenience entry points establish or resume a context containing the normalized timeout and one absolute monotonic deadline. Nested work without an explicit override inherits the parent deadline instead of reapplying a shorter handle default; an explicit nested override still clamps to an existing finite deadline. Explicit zero establishes an infinite CSOT context. The context is restored after every protected call, so concurrent coroutines cannot leak budgets into monitors or unrelated operations.

Topology selection, pool checkout, connection establishment, TLS, authentication, command writes, and aggregate command reads all consume the same absolute deadline through their existing runtime interfaces. Under CSOT, `socketTimeoutMS` and `waitQueueTimeoutMS` do not create shorter per-layer budgets. The command boundary removes legacy write-concern timeout fields and omits `writeConcern` when no fields remain, subtracts the minimum of the latest ten monitor RTT samples after at least two samples, and appends an exact integer `maxTimeMS`; an exhausted RTT-adjusted budget fails before a write. Hello and background monitoring never receive a derived command limit. GetMore retains the client deadline but never receives derived `maxTimeMS`. Database aggregation accepts the same operation-level `timeout_ms` and cursor `timeout_mode` values as collection aggregation, inherits client or database timeouts through its handle state, and captures the original operation context in the returned cursor. Retry attempts and cursor-lifetime continuation therefore share one absolute deadline; iteration mode refreshes only where the common cursor policy requires it, and specifying a mode without a timeout fails before command execution.

The retry executor retains its historical single retry without CSOT and makes eligible attempts until the shared CSOT deadline expires. Without a CSOT context, expiry of the per-attempt socket deadline is retryable once as a legacy transport timeout; an active CSOT timeout remains terminal at the shared deadline. Socket/external timeout errors and server code 50 are converted at the public operation boundary to a distinct timeout error whose cause is the original structured error. Pool checkout expiry is returned without feeding an application error into SDAM, so a wait-queue timeout cannot clear the pool. Runtime-specific socket, TLS, clock, cancellation, and cryptographic behavior remains behind adapters.

Cursor lifetime mode captures the initial context across getMore and allows buffered documents to be returned after expiry. Iteration mode refreshes a new deadline per `next`, omits server `maxTimeMS` for both the initial cursor command and getMore, and is rejected without an effective timeout or for `$out`/`$merge`. Explicit close refreshes the cursor timeout for killCursors even after a timed-out getMore and honors a close-specific override. Sessions inherit or override the client timeout; operation overrides take precedence, and convenient transaction callbacks cannot introduce a new nested timeout.

`mongodb.socket_timeout_executor` derives a fresh per-attempt socket deadline from the injected runtime clock only when CSOT is inactive and passes it only to the command connection's read/write operations. A first timeout therefore neither consumes nor extends the next attempt's configured `socketTimeoutMS` budget. Server selection retains its independent legacy deadline. Timed-out connections are discarded through the topology/pool boundary, allowing a retry, transaction-control retry, or later repeated commit to select a fresh connection without importing runtime-specific networking into higher layers.

### Retryable reads

`mongodb.retry_executor` sits beneath session decoration and above standalone or topology execution. Eligible collection and database `aggregate`, `find`, `findOne`, count, distinct, and database, collection, or index enumeration commands make at most one retry for a retryable server code or label, a network failure, or a legacy socket timeout. The second attempt reuses the exact decorated command and operation identifier, so its logical session and monitoring correlation remain stable while receiving a fresh transport deadline. Aggregate pipelines ending in `$out` or `$merge`, generic commands, and cursor continuation commands are not marked retryable. The normalized `retryReads` setting disables retry orchestration without changing command construction. Database aggregation reaches this policy through the shared aggregate command path; the authenticated handshake fixtures prove both retryable connection-close and server-error recovery, while the direct API regression keeps both write-stage forms single-attempt.

Each attempt uses the operation's existing deadline and performs fresh topology selection or, for a direct standalone, reconnects and repeats hello and authentication after a connection failure. A `SystemOverloadedError` initially deprioritizes the previous server during reselection, while the selector retains its normative fallback when no alternative exists. If the second attempt cannot begin because selection, topology, or pool checkout fails, the first operation error is returned; otherwise the second attempt's result is final. Reconnection remains composed from the existing transport, TLS, hello, authentication, and runtime adapters.

Failures from authentication commands are sanitized without retaining server payloads or credentials, but preserve labels, server identity, timeout state, and numeric codes. A network failure in that sanitizer is explicitly retryable, while `ShutdownInProgress` remains recognizable as code 91. An application authentication failure is reported through the topology before the failed connection closes, so the server becomes Unknown and the synchronized pool clear advances its generation before `ConnectionClosed`. The checkout error is marked as already reported to prevent a second clear at the topology executor. Client construction reuses the monitor handshake capabilities instead of checking out an authenticated application connection, leaving authentication failpoints for the defining operation. A failed handshake publishes checkout lifecycle events but no application command event. Legacy socket deadlines are refreshed after topology selection and checkout, so recovery time does not consume the new connection's command-I/O budget.

Eligible acknowledged inserts, single updates/replacements/deletes, find-and-modify operations, homogeneous eligible collection bulk batches, and eligible client bulk batches use the same executor for retryable writes. The session decorator increments the pooled server session's 64-bit `txnNumber` once before a logical write and therefore reuses it with the same `lsid` and operation identifier on the second attempt. Each eligible collection or client bulk command receives its own transaction number; multi-update/delete batches, generic commands, aggregate write stages, unacknowledged writes, active transactions, standalone servers, and clients with `retryWrites=false` omit it and execute once. Network failures, legacy socket timeouts, and sanitized authentication failures that retain a retryable network marker or handshake code gain the required `RetryableWriteError` label. A retryable cleared-pool checkout also selects a fresh connection for the second attempt while remaining a pool-local signal that cannot mark the server Unknown or clear the pool again. Collection and client bulk batching remain local and use cached hello limits with an OP_MSG allowance of up to 1,000 bytes, bounded by the advertised message-to-BSON headroom, for database, session, transaction, and other operation-agnostic fields. Sizing therefore never introduces a separate observable checkout before the write attempt. Retryable top-level and write-concern responses participate in retry selection, and final-error precedence retains the most recent error that proves a write attempt occurred.

### Single-document CRUD

`mongodb.crud` builds single-document insert and find commands from collection state without importing a runtime-specific module. Insert prepends a lazily generated ObjectId only when `_id` is absent, leaving the caller's immutable BSON document unchanged. The command carries inherited write concern plus supported insert options; `w: 0` uses OP_MSG `moreToCome`, publishes no synthetic command-success event, and returns an unacknowledged immutable result. Acknowledged replies are inspected for both `writeErrors` and `writeConcernError`; structured `write` errors retain the numeric code, labels, complete immutable response, operation index, and unparsed `errInfo`.

`find_one` accepts either an ordered filter or a scalar `_id`, maps validated options to their command names, and always appends `limit: 1` and `singleBatch: true` without a batch size. It returns the first document from `cursor.firstBatch`, returns `nil` when that batch is empty, and treats malformed cursor replies as protocol errors. Raw-data options are emitted only at the negotiated MongoDB 8.2 wire version. Awaitable and exhaust cursor modes remain outside this slice.

### Find cursor lifecycle

`mongodb.cursor` owns immutable, coroutine-aware state for one server cursor: the current cursor identifier, selected server address, buffered batch, position, retrieved count, limit, batch size, inherited comment, and command context. `collection:find`, read-only `collection:aggregate`, `database:aggregate`, generic command cursors, change streams, and the collection, index, and Search-index enumeration paths capture the server selected for the initial command and validate `cursor.firstBatch`; `cursor:next` consumes buffered documents before issuing `getMore` to that same server, validates `cursor.nextBatch`, and updates the opaque 64-bit cursor identifier. Explicit close sends `killCursors` to the same address as well, so a multi-mongos seed list cannot move a live cursor between routers. In load-balanced mode, every cursor-producing command requests and inherits an opaque physical-connection pin from the topology executor. The executor keeps that checkout exclusive while `getMore` and `killCursors` use it, and the cursor returns it exactly once when the initial response or a later batch has cursor id zero or after explicit close. Ordinary deployments ignore the pin request and retain their existing per-command checkout behavior. A positive limit caps getMore batch size to the remaining document count. When the requested limit and initial batch size are equal, the initial command sends `batchSize = limit + 1` as required to avoid an otherwise unnecessary open cursor.

Zero-id exhaustion closes the cursor locally, and an implicit session is returned as soon as the server reports that zero identifier even when documents remain buffered. A timed-out getMore retains its live identifier and implicit session so explicit close can still issue `killCursors`; network and malformed-response failures close local state immediately. A network failure on a load-balanced pinned `getMore` also marks the physical connection unusable but retains its logical checkout until explicit close; that close skips `killCursors`, relinquishes the pin once, and lets the pool discard the failed resource. If `killCursors` itself loses the pinned connection, explicit close suppresses that cleanup failure after relinquishing the logical checkout, while the pool discards the failed resource. A server command error from pinned `getMore` instead preserves the cursor identifier and healthy checkout so explicit close can send `killCursors` on the same connection and return it to the pool. Explicit close refreshes the cursor's inherited timeout after lifetime expiry, honors an operation override, and then deterministically releases the implicit session. Each client keeps a weak registry of live cursors and closes them before its executor connection, so early client shutdown also performs server cleanup. Cleanup is never initiated from a garbage-collection finalizer because runtime command I/O may yield; applications stop early with `cursor:close`, while normal exhaustion and `client:close` are deterministic.

`collection:find` accepts `cursor_type = "tailable"` for capped collections and emits `tailable: true` without `awaitData`. The `tailable_await` mode emits both `tailable: true` and `awaitData: true`, allowing the server to wait before returning an empty batch. For both modes, public `next` performs at most one `getMore`; an empty batch with a nonzero cursor identifier returns `nil` while preserving the cursor, selected server, and implicit session for the next poll. A non-awaitData tailable find with an effective client timeout defaults to iteration timeout mode, while explicit cursor-lifetime mode is rejected and no `maxTimeMS` is added. AwaitData finds reject cursor-lifetime mode; find and aggregate helpers also reject an explicit `max_await_time_ms` greater than or equal to a positive effective timeout before I/O. AwaitData find applies the client timeout to the initial command and refreshes that budget for each public cursor read. Its `getMore.maxTimeMS` is the smaller of `max_await_time_ms` and the remaining deadline after minimum round-trip time; without a maximum await value, only the client I/O deadline applies. The unified blocking-iteration adapter reuses one refreshed deadline across repeated empty batches instead of resetting the budget per `getMore`. The find cancellation token remains attached to later reads. Cancelling a blocked awaitData `getMore` interrupts runtime I/O and returns a structured cancellation error while retaining the logical cursor and implicit session; standalone and pooled executors discard the interrupted physical connection without publishing a false SDAM server failure, and explicit cursor close reconnects to send `killCursors` before releasing ownership.

`collection:watch` constructs a read-only aggregate whose first stage is `$changeStream` and appends the caller's ordered pipeline without mutation. Full-document modes, initial resume positions, and expanded-event selection are copied only into that stage; unknown string modes remain server-validated. Batch size, collation, and comment are routed through the existing aggregate builder, while batch size, maximum await time, comment, and the original session continue through the cursor. Inherited read concern and read preference retain the normal collection aggregation path. Caller option tables and BSON values are never mutated. The resulting cursor is registered with its client before `mongodb.change_stream` wraps it as a distinct immutable public value. The cursor module exposes one internal cooperative advance that consumes buffered data or at most one `getMore`; an empty batch with a nonzero identifier returns without closing. The public stream's `try_next` uses that primitive, while `next` retains the cursor's loop across empty live batches. Both paths preserve selected-server continuation, session ownership, client-close cleanup, explicit close, and closed-state inspection. The unified adapter maps `iterateOnce` only to the cooperative path and maps `iterateUntilDocumentOrError` directly to the public stream's blocking `next` method.

`database:watch` enters the same stage builder, stream wrapper, and recreation callback with aggregate target `1` on the selected database. The shared cursor namespace parser validates the aggregate response's `ns` prefix and retains its collection suffix for subsequent `getMore` and `killCursors`; every successful recreation parses the replacement namespace again. Collection aggregation keeps its fixed collection name. The unified database `createChangeStream` descriptor maps the same declared options to this public helper, so retryable initial aggregates and later iteration resumes continue through the existing executor, selection, session, and timeout layers without test-only behavior.

`client:watch` reuses the database-scoped aggregate boundary with an internal `admin` database handle and adds `allChangesForCluster: true` only to the generated `$changeStream` stage. It retains the same server-returned namespace parsing and recreation callback. The unified client `createChangeStream` descriptor maps directly to the public helper; one exact success path runs through a real sharded deployment, while the remaining retry and authenticated-handshake paths keep their narrowest applicable environments.

Change-stream establishment uses the normal cursor-lifetime timeout context, while each `next` or `try_next` creates one iteration-scoped context shared by its `getMore` and any recreation aggregate. A nested resume inherits the active iteration deadline instead of refreshing the captured cursor context. The operation-timeout layer bounds an explicit `getMore.maxTimeMS` by the remaining deadline minus minimum round-trip time and returns a client-side timeout when no usable budget remains. That timeout leaves the stream object and resume state intact: the following iteration recreates the cursor before advancing. Public construction rejects `max_await_time_ms` greater than or equal to a positive `timeout_ms`, and the unified initial-data adapter maps only the capped-collection options required by the exact tailable-awaitData fixtures. Shared deprecated-option setup can now construct its GridFS bucket entity without server I/O, so every one of those existing operation cases remains runnable.

The cursor validates and retains the optional `postBatchResumeToken` from each aggregate or `getMore` response together with whether documents remain buffered; it also exposes the initial aggregate's `operationTime` only to the change-stream wrapper. A stream begins with `start_after`, then `resume_after`, or no cached token. An empty initial batch with a post-batch token supersedes that position. Otherwise, on wire version 7 or later, an empty initial batch without any caller position or post-batch token saves a valid operation time. Every returned intermediate document caches its `_id`, while the last document in a batch and every empty batch prefer a supplied post-batch token; either token clears the saved operation time. `resume_token()` exposes that immutable BSON value. A returned document without `_id` closes the owned cursor, suppresses cleanup failure, and returns a structured client error.

Iteration treats network failures and CursorNotFound as resumable on every server. MongoDB 4.4 and newer additionally requires the `ResumableChangeStreamError` label; older wire versions use the normative resumable-code set. On a resumable error, the wrapper suppresses cleanup failure from the abandoned cursor and invokes one collection-owned recreation callback. The wrapper chooses exactly one position: `startAfter` while a stream created with that option has returned no event, `resumeAfter` for every cached token after the first event, or `startAtOperationTime` when no token exists and a qualifying initial or explicit operation time is available. Otherwise it recreates the original stage without a position. The callback clears the three original position fields, installs only that choice, and re-enters the normal collection aggregation path with the original pipeline, read preference, and explicit session option. Successful recreations retain the position state for a later independent resume, while caller options remain unchanged. These transitions cover change-stream prose cases 17 and 18; the pinned suite has no machine-readable `startAfter` fixture, while its exact cluster-time event case runs through the public collection stream. The same iteration reads the replacement cursor once without another resume opportunity. A terminal error, a failed resume aggregate, or a second interruption is returned directly. Cluster scope and change-stream-specific timeout behavior remain later v0.5 slices. Runtime-specific networking stays below the existing executor and runtime adapters.

### Update, replace, and delete

`mongodb.crud` maps `update_one`, `update_many`, and `replace_one` to distinct update command models. Atomic update documents must be non-empty and begin with a `$` field; update pipelines must be non-empty BSON arrays containing only documents. Replacement documents use the inverse validation and may not begin with an atomic modifier. The model carries `multi`, `upsert`, array filters, collation, hint, and single-update sort as applicable, while command-level validation, comments, `let`, raw-data, and inherited write concern remain ordered outside the model.

`delete_one` and `delete_many` differ at the command boundary only by their normative limits of one and zero. Acknowledged mutation results expose immutable matched, modified, upserted, or deleted counts, and replacement/update upserts preserve the server-returned identifier. Unacknowledged mutations use OP_MSG `moreToCome`, expose no unavailable counts, and reject collation, array-filter, hint, or sort combinations that their negotiated wire version cannot safely execute. These command builders depend only on BSON and the executor interface; they introduce no runtime-specific networking behavior.

### Core collection read and modify operations

Collection and database aggregation validate an ordered BSON array of document stages and inspect only the final stage to identify `$out` or `$merge`. Database commands use aggregate target `1`; collection commands use their collection name. Read pipelines inherit read concern. Write pipelines inherit write concern, add read concern on MongoDB 4.2 and newer, carry the inherited read preference through replica-set selection and OP_MSG command construction, ignore an initial batch size, and synthesize an exhausted cursor after an unacknowledged OP_MSG send. All other aggregate results enter the existing cursor model, so batch size, getMore comment and maximum await time, explicit kill, and client-close cleanup have one implementation. Database aggregation derives the cursor collection from the response namespace because administrative pipelines are not tied to a collection named by the caller.

`count_documents` builds the normative `$match`, optional `$skip` and `$limit`, and `$group` pipeline and parses its single cursor result, treating an empty batch as zero. `estimated_document_count` intentionally uses the metadata-based `count` command, while `distinct` validates and returns the server's BSON values array. The deprecated `count` helper sends that legacy command with its filter as `query`, translates the CountOptions fields, applies inherited read concern and read preference, and extracts the non-negative integer `n`. It enters the shared retryable-read executor: without CSOT an eligible command failure is retried exactly once, while `retryReads=false`, a non-retryable failure, or an active transaction produces no extra attempt. Client-, database-, collection-, and operation-level `timeout_ms` values flow through the same absolute operation deadline; retries reuse its remaining budget, derived `maxTimeMS`, selection, pool, and socket limits instead of refreshing the timeout.

The deprecated `map_reduce` helper accepts JavaScript strings or BSON code values plus a collection name or ordered output document. It encodes the command's explicit query, sort, scope, collation, finalizer, validation, timing, and execution options. Inline output is selected as a read, inherits read concern, omits write concern, and returns the server's `results` array; output-producing commands select as writes, apply only a non-default inherited write concern, validate write-concern errors, and return the server's `result` value. Both forms are intentionally single-attempt: the Retryable Reads specification excludes `Collection.mapReduce()`, so an eligible first-attempt failure is returned even when `retryReads` is enabled.

These read helpers use the same deadline/cancellation executor boundary as find. Their internal `raw_data` option, shared by list-collection and create/list/drop-index administration, is validated as a boolean and appended as `rawData` only when the selected server advertises wire version 27 or newer (MongoDB 8.2); older servers omit it without changing the operation result shape.

The three find-and-modify helpers share one ordered `findAndModify` builder but retain update-versus-replacement validation. Delete sets `remove`; update and replacement set `update`, optional upsert, and a `new` boolean derived from the public `before`/`after` choice. Projection maps to the wire-level `fields` name. Array-filter and hint constraints are checked before unacknowledged I/O, write and write-concern errors reuse the structured write-error path, and BSON null results map to Lua `nil`.

### Collection bulk writes

`mongodb.bulk` defines immutable insert, update, replacement, and delete models shared by `collection:bulk_write`; `insert_many` builds the same insert models internally. Ordered execution preserves adjacent command-kind runs and stops on the first write error. Unordered execution groups compatible models while retaining each model's original 1-based request index for upsert identifiers and structured write errors. Every command in one call carries the same operation identifier.

Batch construction observes `maxWriteBatchSize`, then encodes each candidate `documents`, `updates`, or `deletes` sequence locally against the cached hello limits. Its OP_MSG allowance is capped at 1,000 bytes and bounded by the advertised message-to-BSON headroom, so database, session, transaction, and other operation-agnostic fields fit without a separate connection checkout. Individual insert and replacement documents are also checked against `maxBsonObjectSize` where an unacknowledged server cannot report the violation. Networking, TLS, and cryptography remain behind their existing runtime adapters.

Acknowledged responses merge counts, upsert identifiers, write errors, write-concern errors, labels, and raw response documents into immutable results or structured partial-result errors. Unacknowledged requests use `moreToCome`; ordered multi-batch requests acknowledge intermediate batches so the driver can preserve stop-on-error semantics before sending the final unacknowledged batch.

### Client bulk writes

`mongodb.client_bulk` owns immutable namespace-scoped models that are intentionally distinct from `mongodb.bulk` collection models. It accepts insert, update-one, update-many, replacement, delete-one, and delete-many models. Updates accept atomic-modifier documents or non-empty pipeline arrays; replacements reject an atomic modifier in the first field. Model options are copied into private state and validated by model kind. Updates translate explicitly supplied values to the bulk command's `updateMods`, `multi`, `upsert`, `arrayFilters`, `collation`, `hint`, and `sort` fields; deletes translate their filter, `multi`, and explicitly supplied `collation` and `hint`. Caller BSON remains unchanged. `client:bulk_write` generates missing ObjectIds without mutating caller documents, places generated `_id` fields first, and emits one or more `admin` `bulkWrite` commands with separate `ops` and `nsInfo` OP_MSG document sequences. Each command contains at most the selected server's `maxWriteBatchSize` operations, rebuilds `nsInfo` in first-use order from only the namespaces referenced by that batch, and gives every operation the corresponding zero-based local namespace index. The encoded command, operations, and namespace documents are also limited to `maxMessageSizeBytes - 1000`, reserving the normative allowance for operation-agnostic fields and OP_MSG framing. A document or namespace that cannot leave room for one operation returns a client error before any command is sent. Successful counts and verbose result maps accumulate across the batches at original model positions, and every command retains one logical operation id. The command explicitly sends `errorsOnly: true` and defaults `ordered` to true.

Acknowledged responses validate every top-level summary count and consume the complete server result cursor before returning. `verbose_results = true` sends `errorsOnly: false` and populates immutable insert, update, and delete result maps at the original 1-based model positions; summary results omit those maps. Insert details retain the exact caller or generated identifier, update and replacement details retain match, modify, and upsert values, and delete details retain their counts. Individual `ok: 0` cursor documents become immutable structured write errors with the server code, message, optional `errInfo`, original 1-based model index, and exact failed wire operation. Ordered execution stops after the first observed individual failure; unordered execution consumes the cursor and returns every observed failure sorted by original index. Across batches, unordered write errors continue execution and accumulate after remapping their local indexes, while an ordered write error prevents later commands. Write-concern errors never stop batching and remain individually available in the final exception. Any preceding successful batch counts and verbose details remain in the immutable partial result. Partial-result presence follows the server specification rather than nonzero summary counts: an ordered failure has a partial result only when its first error index is greater than zero, while an unordered failure has one only when `nErrors` is smaller than the submitted model count. The partial value reuses the immutable public result shape, and verbose maps contain only successful cursor documents at their original indexes. A nonzero cursor issues `getMore` against `admin.$cmd.bulkWrite` until exhaustion. A failed `getMore` halts iteration and immediately attempts one `killCursors` against the live `admin.$cmd.bulkWrite` cursor. The client-bulk exception retains the structured `getMore` cause and every confirmed verbose result in its immutable partial result; a failed cleanup remains available as the structured `cleanup_error` detail instead of being discarded. A top-level `writeConcernError` is reported only after that cursor is exhausted; its code, code name, message, `errInfo`, and response labels remain structured, while confirmed successful operations remain available through the immutable partial result.

A top-level executor failure halts before cursor work and is wrapped by the client bulk write boundary with the original structured cause, category, code, code name, message, labels, timeout state, and raw command reply. The envelope retains a partial result accumulated from earlier successful transport batches; a failure before the first confirmed result has no partial result.

Each acknowledged client batch outside a transaction is retryable only when every update and delete is single-document. The shared retry executor makes at most one new attempt after an eligible network, authenticated-handshake, labeled top-level, or labeled write-concern failure, reusing the batch lsid, transaction number, and operation identifier. Attempt responses are parsed and merged only after that executor returns, so a successful retry cannot duplicate counts or verbose results; multi-write batches and clients with `retryWrites=false` remain single-attempt. An unacknowledged concern is valid only with unordered, non-verbose execution; invalid ordered or verbose combinations and an explicit session return their normative client errors before network I/O. Every split `w: 0` command uses OP_MSG `moreToCome` without an implicit session on the same selected connection and operation identifier, and the immutable result exposes only `acknowledged = false`. Acknowledged execution carries one caller-owned explicit session or one operation-owned implicit session across every split `bulkWrite`, result `getMore`, and cleanup command; the implicit session ends after the complete operation. Causally consistent explicit sessions add their advanced `afterClusterTime` through the shared session executor, while ordinary sessions add no read concern. Active transactions treat every batch as acknowledged, omit inherited write concern from `bulkWrite`, and reject an explicit operation write concern before I/O. Every batch and result `getMore` retains the same `lsid`, transaction number, and `autocommit: false`; only the first command adds `startTransaction`. Shared transaction error handling retains a mongos pin after a non-transient client-bulk error and clears it after network or server-labeled transient failures.

Command construction preserves explicit `ordered`, `bypass_document_validation`, arbitrary BSON `comment`, and `let` values, normalizes an operation write concern over the inherited client concern, and relies on the shared executor for Stable API decoration and command monitoring. Monitoring reconstructs the logical `ops` and `nsInfo` arrays from both OP_MSG sequences. The internal `raw_data` option is emitted as `rawData` at wire version 27 or newer and silently omitted on MongoDB 8.0, matching the existing read/write management gate without advertising the internal option in the public overview.

`timeout_ms` creates one operation-timeout context around the complete client bulk call. Its absolute deadline reaches every split `bulkWrite`, the retry executor, result `getMore`, and best-effort `killCursors`; each command therefore derives its remaining server and socket budget instead of restarting the requested timeout. A timeout retains every result confirmed before the failed command, and live result cursors receive one cleanup attempt under that same deadline. Runtime clocks and cancellation remain behind the shared runtime and executor adapters.

Seventy exact upstream client-bulk cases now cover null identifiers, empty-model validation, update/replacement sort and validation, result and partial-result modes, write-concern and top-level command failures, mixed namespaces, ordered and unacknowledged modes, command and model options, pipelines, Stable API decoration, sessions, causal consistency, transactions, mongos pinning, retry eligibility, retryable network, authenticated-handshake, top-level and write-concern failures, and all six raw-data version branches.

The directly coupled upstream collection-bulk CSOT identity proves the same whole-operation timeout boundary with live blocked commands. Load-balanced connection pinning for result `getMore` remains at the corresponding continuation boundary.

Unsupported unified model names fail explicitly at the adapter boundary, while their exact fixture identities remain assigned to those slices. All networking continues through the existing executor and runtime adapters.

### Database, collection, and index administration

`database:run_command` accepts a non-empty command name or ordered BSON document and returns the server reply through the shared operation/session executor. Generic commands are selection reads: they default to primary independently of inherited client or database preferences, while an explicit operation read preference is normalized and passed through the topology selector. The command document itself receives no inherited read concern or write concern; explicit command fields remain untouched. The unified adapter validates `commandName`, orders that field first when fixtures provide a differently ordered command document, and translates the unified read-preference document at the adapter boundary. Network, TLS, and cryptographic behavior remain behind the existing runtime and command-executor adapters.

`database:run_cursor_command` applies that same initial-command selection contract but requires a cursor response immediately and returns the shared public cursor model. The response namespace supplies the collection name; a missing cursor, malformed namespace, identifier, or first batch is a structured protocol failure. Optional `batch_size`, `max_await_time_ms`, and `comment` values decorate later getMore commands without mutating the caller's initial command. A supplied `timeout_mode` requires `timeout_ms`; `cursor_type = "tailable"` makes each read issue at most one getMore and preserves a nonzero cursor id across an empty batch, while cursor-lifetime timeouts remain incompatible and await-data command cursors remain deferred. The first selected address is captured below the retry/session layers and pins every continuation and explicit kill to that server. In load-balanced mode, the selected physical connection remains exclusive to the cursor until exhaustion or close. One implicit session is retained across the initial command and getMore sequence, while an explicit session remains caller-owned. The exact `checkMetadataConsistency` fixture exercises this path through mongos, and the exact capped-collection fixture proves empty-batch liveness and explicit cleanup through a standalone. CMAP assertions and timeout-close cleanup run through exact release conformance cases.

`mongodb.admin` builds list, create, modify, rename, and drop commands for databases, collections, and indexes without importing any runtime provider. The public client, database, and collection handles supply their inherited concerns, negotiated wire version, executor, and shared cursor registry. Collection creation preserves clustered-index, time-series, and `change_stream_pre_and_post_images` documents plus time-series expiration in the ordered command. Collection modification exposes validator updates, index constraint transitions, and the same ordered image document through `database:modify_collection`. `collection:rename` validates the destination collection name, sends fully qualified source and destination namespaces to the `admin` database, and preserves optional target replacement, comment, session, deadline, cancellation, and inherited write concern. The unified createCollection and modifyCollection descriptors map nested documents directly to the public options, while unified rename delegates to the public collection method; exact MongoDB cases verify these command shapes without adapter-side BSON reconstruction. Command failures preserve root-level server details such as constraint violations and validation `errInfo`. Write commands apply inherited write concern and retain write-concern response details; collection and index drops treat namespace-not-found as an idempotent success.

Database enumeration wraps the command's returned array in an exhausted local command cursor. Database and collection enumeration force primary selection in replica-set topology independently of the inherited client preference; Single topology still permits a directly connected secondary, and standalone and mongos selections retain their normal routing. Collection and index enumeration use the server cursor namespace to construct getMore and killCursors commands, then share the existing cursor lifecycle and client-close cleanup. A listCollections comment is not repeated because the server inherits it, while listIndexes explicitly carries its comment onto getMore as required by the index-management specification.

Immutable index models retain ordered key documents, validate supported directions and option types locally, and generate deterministic key-direction names. `create_index` delegates to the same createIndexes path as multi-index creation. Create, list, and drop operations inherit or override one CSOT deadline, including `list_index_names` cursor collection and the all-index `drop_indexes` adapter. The boundary rejects `commit_quorum` before MongoDB 4.4 and gates internal raw-data fields on the MongoDB 8.2 wire version; all network behavior remains behind the command executor and runtime adapters.

Search-index creation validates ordered BSON models with a required definition plus optional name and `search` or `vectorSearch` type. `collection:create_search_index` sends one model through the common `createSearchIndexes` path and returns the single server-reported name, preserving a generated default when the model omits one. `collection:create_search_indexes` accepts a dense Lua array, retains model order, forwards the normative empty array to the server, and returns an immutable ordered name list; malformed success replies are protocol failures. `collection:list_search_indexes` executes a primary-selected aggregation containing one `$listSearchIndexes` stage, omits the stage's name field when no filter is provided, and returns the shared command cursor. Its aggregation options retain initial batch sizing, getMore behavior, sessions, cancellation, and deadlines while the command deliberately contains neither collection read concern nor write concern. `collection:update_search_index` validates a non-empty UTF-8 name and ordered BSON definition before sending their exact values through `updateSearchIndex`; operational failures remain structured return values. `collection:drop_search_index` applies the same name validation, sends the exact `dropSearchIndex` command, and treats NamespaceNotFound as idempotent success while preserving every other operational error. Creation, listing, update, and drop commands all omit inherited read and write concerns while retaining sessions, deadlines, monitoring, and primary selection where required. The unified adapter converts model arrays and nested aggregation options at its boundary instead of widening the public API contracts. These paths do not import a runtime or synthesize Atlas behavior.

### SDAM descriptions and transitions

`mongodb.sdam` is the side-effect-free phase-one SDAM core. It parses modern `hello` and legacy `ismaster` replies into immutable server descriptions, including replica-set membership, topology versions, generations, wire compatibility, election metadata, session timeout, tags, and server limits. Topology updates return new immutable descriptions and leave every prior snapshot unchanged, so monitor scheduling and selection can publish consistent views without sharing mutable transition state.

The transition table covers Single, Unknown, Sharded, LoadBalanced, ReplicaSetNoPrimary, and ReplicaSetWithPrimary descriptions. It discovers and removes replica-set members, rejects mismatched set names and stale primaries, invalidates an older primary when a newer one appears, preserves monotonic election metadata, ignores stale topology versions and connection generations, and computes topology-wide wire compatibility and logical-session timeout. A validated `loadBalanced=true` URI constructs one permanently compatible `LoadBalanced` description whose sole server has only its address and `LoadBalancer` type. The v1 client range is wire version 21 through 27, matching MongoDB 7.0 through 8.2.

This module performs no I/O and imports no runtime provider. `mongodb.topology` owns the mutable orchestration layer above it: one independent monitor task and dedicated unauthenticated connection per ordinarily discovered server, awaitable hello with the last topologyVersion when supported, a separate RTT connection, topology-change signaling, pool ready/clear transitions, and heartbeat plus SDAM event publication. Load-balanced opening instead promotes the single seeded server from `Unknown` to `LoadBalancer` through a synthetic description transition, publishes the required five opening events, and creates no monitor or RTT task. Selection returns that server directly for every valid read or write preference, bypassing replica-set filters, custom selectors, deprioritization, and the latency window; non-primary OP_MSG reads receive the same `$readPreference` document used for mongos. Explicit `stream` selects awaitable hello when a server supplies topologyVersion and falls back to polling when it does not; explicit `poll` always waits the heartbeat interval after success and never starts the extra RTT task. `auto` resolves to polling when the runtime metadata environment matches the same FaaS detector used for handshake metadata and to streaming otherwise, so core scheduling never reads process environment directly. Once an initial check discovers topologyVersion, streaming mode begins its first awaitable hello immediately instead of sleeping for heartbeatFrequencyMS; each successful streamed reply starts the next receive without a polling delay. Streaming mode records the initial monitor handshake as its first RTT sample, then schedules RTT probes independently of awaited hello after each heartbeat interval. RTT probes update only average and minimum RTT fields without publishing monitoring events, while a main monitor failure resets the sample window. Every monitor handshake and later hello check uses a fresh base `connectTimeoutMS` deadline; an awaited hello extends that deadline by its `maxAwaitTimeMS`, which is `heartbeatFrequencyMS`, while a zero connect timeout remains unlimited. Command, network, and timeout failures close that monitor connection, publish one Unknown transition, clear the matching pool generation once, and recover on a new monitor connection. Timeout failures retain their structured timeout marker so the pool clear receives the interrupt distinction even when the operational category is network. Application-error orchestration separates field validation, stale-error rejection, error classification, and the resulting state transition into local helpers. A fresh network, handshake, not-primary, or shutdown error publishes the server-description transition before clearing the pool, requesting a monitor check, and cancelling any in-flight awaitable check; recovery therefore uses a non-awaitable handshake that restores RTT before selection resumes. Selection failure requests an immediate scan while respecting the minimum heartbeat frequency. Discovered members receive monitors and pools; removed members are closed. Opening publishes the seeded description from an empty Unknown snapshot. Shutdown marks the topology closed, cancels shared monitor work, replaces the live snapshot with an immutable empty Unknown description, and publishes that final topology-description change for Single, replica-set, and Sharded topologies. It then cancels individual monitor I/O and sleeps, waits for the tasks to finish, closes monitor connections and pools, publishes server-close events before topology-close, and ignores late monitor results. `TopologyClosed` remains the last SDAM event, and a repeated close publishes nothing. The exact monitoring fixtures include the static load-balancer sequence alongside the existing mode, failure, deadline, cancellation, and timeout cases; the exact load-balanced discovery fixture verifies the permanent synthetic description, and the two-mongos lifecycle fixture proves the final `Sharded`-to-`Unknown` transition occurs before `TopologyClosed`.

An application network error cancels the active awaited hello through its runtime token. The monitor closes that dedicated connection and discards any response or error returned after cancellation before SDAM processing, so a superseded check cannot replace the newer Unknown description or publish duplicate server and pool events. The next requested check uses a fresh connection and restores the server through the normal non-awaitable handshake; task and connection ownership remain unchanged.

### Server selection

`mongodb.selection` composes immutable read preferences with an immutable SDAM topology snapshot. It applies topology and operation rules first, retries without address deprioritization when the preferred set is empty, then filters replica-set reads by max staleness and the first matching tag set. An optional application selector runs before the final `localThresholdMS` latency window. Selection from that window uses the power-of-two choice rule against caller-supplied operation counts supplied by each connection pool.

Max staleness is validated against both the 90-second minimum and `heartbeatFrequencyMS + 10 seconds`. Estimates use the normative with-primary and no-primary formulas over hello `lastWriteDate` and local `lastUpdateTime` values. RTT samples use the specified 0.2/0.8 exponentially weighted moving average. Invalid preferences and unavailable RTT data return structured configuration errors, while an exhausted selection returns a structured timeout whose message and `topology` field describe the final immutable snapshot.

The selection layer is pure and never sleeps or performs I/O. It evaluates the snapshot supplied by its caller; `mongodb.topology` owns monitor wakeups and topology-change waits and passes the final snapshot into timeout errors. The unit gate runs all 88 pinned JSON server-selection filtering fixtures, 32 max-staleness fixtures, 7 RTT vectors, and 8 operation-count choice distributions. Their YAML files duplicate the same cases. The five structured server-selection logging fixtures are assigned to additional activity `ADV-009`, which owns logging and telemetry.

### Connection pools and CMAP

`mongodb.pool` owns one coroutine-safe pool per server. It starts paused, enters the ready state explicitly, assigns monotonically increasing connection identifiers, and maintains distinct pending, available, and checked-out sets. A FIFO wait queue enforces `maxPoolSize` and `maxConnecting`; its operation count includes queued, connecting, and checked-out work so server selection observes actual load. Cancellation, timeout, setup failure, check-in, clear, and close each release their owned capacity exactly once.

Connection establishment is an injected adapter that returns an already connected, TLS-upgraded, handshaken, and authenticated resource or a structured error. The pool imports the runtime contract, structured-error layer, and BSON tag recognition needed to validate service identifiers. It contains no socket, TLS, cryptography, hello, or authentication implementation. Network and timeout failures during setup receive the backpressure labels required by the pooling specification, except authentication and explicitly exempt failures. A load-balanced client uses the static topology's application pool for capability discovery because it has no monitor connection: it checks out one fully established resource, snapshots its hello capabilities, and checks it back in before exposing the public client. Every later pool creation uses the same load-balanced handshake policy. Ordinary monitor and application handshakes, authentication, and compressor negotiation retain their existing paths.

Each live pool checkout is tagged as cursor, transaction, or other work and relinquishes that tag exactly once on check-in, including when the physical resource is discarded. Load-balanced wait-queue timeout errors snapshot those three counts, while ordinary pools retain their established timeout message. Generation changes make available connections stale, clear queued work, and optionally interrupt pending and checked-out connections. An interrupting clear closes the matching generation's physical resource immediately but retains the logical checkout until the operation returns it, so `ConnectionCheckedIn` precedes `ConnectionClosed` and the resulting read or write error remains retryable. Load-balanced connections retain the validated `serviceId` from their completed handshake and take their generation from a service-specific map. A targeted clear increments only that service generation, leaves the pool ready and its wait queue intact, and invalidates only matching connections; other services remain reusable. Application-error handling compares both the connection generation and service identifier before clearing, so an error from an older service generation is ignored. In load-balanced mode, pre-handshake errors without a service identifier bypass SDAM, while post-handshake command and authentication failures may clear their service generation without replacing the permanent topology or synthetic `LoadBalancer` server description. Maintenance prunes idle or closed resources and restores `minPoolSize`; a failed background establishment releases its pending and total capacity and delegates the pool-clear decision to SDAM. Pool close cancels any in-flight background establishment and awaits that maintenance run before publishing `ConnectionPoolClosed`, so its Copas socket coroutine and pending capacity cannot escape into a later client lifecycle. Non-load-balanced authentication failures clear and pause the pool until a successful monitor check readies it, while initial-handshake network failures carrying `SystemOverloadedError` leave the pool ready and schedule a delayed population attempt. The monitored topology connects pool readiness and clearing to server-description and application-error transitions. Network and shutdown application errors clear before the failing connection is checked in, post-handshake network timeouts do neither, and pool checkout errors never re-enter application-error handling. Requesting CMAP listeners selects the monitored pooled executor even without SDAM listeners. Pool and connection lifecycle events are immutable and published in normative order.

A targeted `ConnectionPoolCleared` event carries the cleared BSON `serviceId`; traditional whole-pool clears retain a nil service identifier. The unified collector preserves that field for `hasServiceId` assertions without changing event order.

The integration gate executes all seven pinned establishment, cancellation, and `maxConnecting` timing fixtures against an injected asynchronous connection adapter; their YAML counterparts duplicate the same cases. Replica-set application connections and standalone clients with a positive minimum use those pools. Five exact authenticated-standalone SDAM fixtures cover authentication command, miscellaneous, network, timeout, and shutdown failures: each marks the server Unknown, clears the pool before closing the failed connection, and recovers for the next write. Eight application-error fixtures cover find/insert network errors, post-handshake timeout suppression, concurrent shutdown errors, pool-clear ordering before check-in and failed-auth close, and retryable PoolCleared checkout recovery on a replica set. Three replica-set interrupt-in-use fixtures prove monitor-timeout clears carry the CMAP interrupt flag and that interrupted reads and writes retry on a new checkout. The minimum-pool fixture separately proves that a transient code-91 handshake failure clears without leaking capacity and permits monitor readiness to replenish the minimum afterward. Handshake metadata conformance covers baseline transmission, environment discovery, bounded-size reduction, wrapper updates, and the pinned unified metadata lifecycle fixture. The two JSON CMAP logging fixtures are assigned to additional activity `ADV-009`, which owns logging and telemetry.

Dependencies point downward. API objects do not call Copas, LuaSocket, LuaSec, native digest modules, or operating-system entropy modules directly; they depend on runtime and protocol interfaces. The same boundary supports deterministic unit fakes.

`mongodb.runtime.contract` contains the dependency-free runtime validation, deadline, cancellation, and error helpers used by runtime implementations. The public `mongodb.runtime` façade re-exports that contract and constructs the default Copas adapter, so adapters never depend back on their own façade. `planning/check_architecture.py` scans every production Lua module and literal `require`, rejects dependency cycles, and permits direct OS, filesystem, socket, scheduling, TLS, native-module, and cryptography access only inside `mongodb.runtime`. `make test-architecture` is part of the fast gate, and diagnostics name the exact cycle or source line that crosses the boundary.
